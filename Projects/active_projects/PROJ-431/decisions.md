| 2026-05-16 | **Adopt the explicit deployable-group model over the typed-carried-items fallback** | TD-10 §"Goal / End State" offers two options. The fallback (typed `BayInventory` only) would leave `Fleet.group_kind` as the discriminator across 14+ files and the **ten** fleet-action handler guards — the most error-prone part of the current state. The full split costs ~3x more LLM time (~2.5–3 hours total vs ~30–45 min) but the mediation surfaces (`IIssuerAdapter`, `MineGroupService`, `CarriedVehicle`, `_split_mine_groups_from_fleets`) already exist, so the marginal complexity is moderate. Per the user's `feedback_capability_missing_rejects_not_degrades.md` preference, a typed model that makes "fleet vs deployed group" a compile-time distinction beats a runtime-string discriminator guarded in ten handlers. |
| 2026-05-16 | **Remove the synthetic mine-carrier `ShipInstance` in Phase 2 — do not refactor it** | The `_seed_mine_group_carrier` ship (`design_id="mine_carrier_synthetic"`, `current_hp=0`, `is_alive=True`) exists solely to keep the serializer/DTO surface usable. It is documented in `minefield_resolver.py:144-163` as a workaround, and its presence is so leaky that `spec_compiler._split_mine_groups_from_fleets` exists specifically to filter it back out at the combat boundary. Replacing it with a `MineGroup` dataclass that owns `mines: list[CarriedVehicle]` directly deletes both the fake ship and the boundary filter. |
| 2026-05-16 | **`DeployedGroup` is a sibling to `Fleet`, NOT a subclass** | Inheriting from `Fleet` would carry the entire fleet surface (movement, strategic orders, fleet-action handlers) into deployed groups — exactly the surface `_reject_if_non_fleet_group` guards against today. Sibling typing makes "you cannot issue Move/Warp/Build against a `MineGroup`" a compile-time impossibility, not a runtime check. |
| 2026-05-16 | **`Empire.deployed_groups: list[DeployedGroup]` is a separate collection from `Empire.fleets`** | Replaces the current "filter `empire.fleets` by `group_kind`" pattern across 14+ files. Combat spec assembly, minefield resolution, AI controllers, and UI all switch to `isinstance`-based dispatch off the new typed list. |
| 2026-05-16 | **Land Phase 1 (typed `BayInventory`) early to unblock PROJ-425's cargo batch** | PROJ-425 (TD-06) Phases 0–4 do safe upstream ShipInstance slimming and may run before this project. PROJ-425's deferred cargo/deployable forwarder-demolition batch is gated on this project's Phase 1 because the forwarders' replacement surface (`bay_inventory.bay` / `bay_inventory.pods`) only exists after Phase 1. Phase 1 is independently shippable per the TD plan, so we treat it as a deliverable in its own right, not a stepping-stone. |
| 2026-05-16 | **Phase boundaries are PR boundaries** | Per TD-10 §"Execution Preconditions" rule 4: when the full split is chosen, each phase must commit independently. Phase 1 ships alone, Phase 2 ships alone, Phase 3 ships alone, Phase 4 is cleanup/docs only. This bounds blast radius and makes the cumulative review at each phase boundary tractable. |
| 2026-05-16 | **Delete `CarriedVehicle.from_any()` in Phase 1 — do not preserve it** | Once `bay_inventory.bay` is homogeneous `list[CarriedVehicle]`, the runtime discriminator that returns `None` for drop-pod-shaped entries is dead. Removing it forces every consumer to migrate to the typed slot — no half-migrated state where some readers still use `from_any` and some use `bay_inventory.bay`. Per CLAUDE.md root-cause rule. |
| 2026-05-16 | **Delete `_split_mine_groups_from_fleets` in Phase 2 — do not parameterize it** | PROJ-426 (TD-01) is reworking the spec compiler and the validated TD-01 plan adds a temporary `mine_group_filter` parameter to the assembler. Once minefields live in `empire.deployed_groups`, the assembler walks the new typed list and the filter is moot. Per CLAUDE.md root-cause rule: when a system is replaced, remove the old path and update all callers. |
| 2026-05-16 | **Delete `_reject_if_non_fleet_group` in Phase 3 — do not keep it as a "double safety"** | The guard exists because `Fleet` is the bus for both real fleets and deployed groups. Once deployed groups have their own typed model, deployed-group instances cannot reach `Fleet`-typed handler parameters at all — the protection becomes structural. Keeping the runtime guard "just in case" would preserve a defensive check that can never fire, masking future type-system erosion. |

New save shape rejects old saves at load time. This unblocks the cleanest possible Phase 1 / Phase 2 implementations. |
