# The stable API surfaces you build on (post-PROJ-436 Phase 7)

- `game/strategy/data/container.py::Container` — the unified
  storage abstraction. Three internal slices: resources (dict[str,
  float]), items (list[ItemRef]), population (dict[str, int]).
  Mass-cap accounting. Public ops: `add(containable, quantity) ->
  AddResult`, `remove(...) -> RemoveResult`, `accepts(containable)
  -> bool`, `contents() -> Iterable[ContainerEntry]`,
  `mass_used` / `mass_remaining`, `to_dict` / `from_dict`.
- `game/strategy/data/containable.py` — `ContainableKind`
  (RESOURCE / ITEM / POPULATION), `ResourceContainable`,
  `ItemContainable`, `PopulationContainable`, `ItemRef`. Resource
  mass resolves via Core `ResourceCatalog`. Population default
  0.1 tons / individual per user directive.
- `game/strategy/data/bay_inventory.py::BayInventory` — four-slot
  per-ship inventory (bay, pods, resources, population).
  `container_view(capacity_mass, policy)` returns a snapshot
  Container projection for UI consumption.
- `game/strategy/data/ship_instance.py` —
  `cargo_container()` and `consumable_container()` snapshot views;
  manager-API canonical writes via `ship._cargo_mgr` /
  `ship._resource_mgr` (`get_all_levels` / `set_level` /
  `replace_levels` / `get_current_resource` /
  `get_all_cargo` / `set_cargo` / `total_cargo_units` /
  `has_cargo`).
- `game/strategy/data/planet.py` — `stockpile` /
  `max_stockpile` / `staging_yard` are `@property` over private
  `_-prefixed` fields. Writes route through `IPlanetMutator` or
  Planet's own helpers (`add_to_stockpile` /
  `consume_from_stockpile` / `add_to_staging_yard` etc.).
- `game/strategy/data/empire.py::Empire.resource_pool` — pure
  aggregation over `self.colonies[*].stockpile`. NOT a fleet pool.
  No setter.
- `game/core/resources.py::ResourceCatalog` — Core-layer single
  source of truth. `all_ids()` / `all_definitions()` /
  `get(rid)` / `has(rid)` / `get_mass_per_unit(rid)`. The
  catalog is loaded once at app start; UI consumers can
  freely call `ResourceCatalog.from_json()` (existing
  convention used at 16+ sites).
- `game/simulation/components/abilities/container.py::ContainerAbility`
  — the unified storage ability declared on components
  via `data/components.json` shape
  `{capacity_mass, allowed_kinds, allowed_type_ids}`. Parity
  helpers `container_view_from_resource_storage()`,
  `container_view_from_cargo_storage()`,
  `container_view_from_vehicle_bay()` compile legacy abilities
  into the unified shape.
- `game/strategy/validation/transfer_validator.py::TransferValidator`
  — post-Phase-7 validator: `_is_known_cargo_type(cargo_type)`
  consults `ResourceCatalog.has()` + a `_CATEGORICAL_CARGO_TYPES`
  frozenset of `{"passengers", "drop_pod", "vehicle"}`.

# Sub-phase template — when to use sub-phases vs single-cutover

Mirror the PROJ-436 pattern:

- If a phase has narrow scope (Phase 0 read-only research, Phase 4
  small UI sweep) — collapse to a single commit.
- If a phase has wide blast radius (Phase 1 source/dest browsing
  potentially touches view model + controller + fleet_data_source
  + multiple test files; Phase 3 mixed-content display) — use the
  PROJ-431 sub-phase model (Xa substrate / Xb-Xe migration /
  Xf cutover). Audit blast radius FIRST.

Direction rule: when changing a contract, land the new shape as a
projection over the old; migrate callers; delete the old in the
final cutover commit of that phase.
