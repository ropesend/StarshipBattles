| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-04-26 | Project initialized | Starting point for Universal IAbilitySource Framework + Storm/Facility Migration |
| 2026-04-26 | **Storms unify with facility sector effects under a single `IAbilitySource` framework** rather than living as a parallel system | User asked: "the system should be unified so that storms simply have abilities with sector scope, and show up in the sector effects, just like the other effects from a complex would." Eradicates parallel-system divergence per CLAUDE.md Rule 3 (Clean-Sheet Design). |
| 2026-04-26 | **Discovery model:** `IAbilitySource` protocol + unified iterator (rejected per-source-type collectors and zone-index extension) | One code path; trivial to add new source kinds later via adapter pattern. Per-source-kind quirks (owner filtering, activation state) handled inside source-specific adapters that wrap raw entities. |
| 2026-04-26 | **Data location:** per-type JSON registries (`storm_types.json`, etc.) with type templates; instance values rolled at galaxy creation when needed | Matches the existing storms.json idiom. Clean separation between types (template) and instances (rolled values). User confirmed: "I like the per-type json registries, but some values will need to be generated at galaxy creation, damage amounts etc..." |
| 2026-04-26 | **Rollout:** six PROJ-XX projects (PROJ-300..305) — framework first, then one source kind per project | User confirmed: "I want a plan for all 7, it can be done in multiple projects each broken into phases, but I want a plan for full implementation now." |
| 2026-04-26 | **Storm stacking:** overlapping storms MULTIPLY (no shared `stack_group`) | Preserves current `AreaEffectManager` behavior verbatim. User chose this over MAX. Subtle behavior change in combat: today's `stack_group="storm_shield_interference"` MAX-groups in combat (two ion storms = 0.5×); under the new design, two ion storms = 0.25× (multiply). Storms emit each provider as its own ungrouped entry. |
| 2026-04-26 | **Field naming:** `damage_per_tick` / `fuel_drain_per_tick` → unified `rate` field meaning per-turn | User confirmed renaming. JSON value `0.5` means "0.5 hull/turn"; engines internally `/100` to derive per-tick. Matches the `multiplier` field convention for multiplier-style abilities. |
| 2026-04-26 | **Storm detail panel:** keep, but show only lore (name + description); effect breakdown moves entirely to Sector Effects | User chose this option. Lore description ("Electromagnetic disturbance...") is good flavor that doesn't fit in an effects-list ontology. Effect numbers are redundant if also shown in Sector Effects. |
| 2026-04-26 | **Facility-projected hazards allowed:** facility components MAY declare `EnvironmentalDamage` / `FuelDrain` over a sector | User confirmed. The framework's reach is the point — once storms emit normal sector abilities, facilities can too. Enables future designs like an offensive "Plasma Projector" complex with `scope: enemy_sector`. |
| 2026-04-26 | **Aggregation extension:** add `aggregate_rates` (intra-MAX, inter-SUM) alongside existing `aggregate_multipliers` (intra-MAX, inter-MULTIPLY) | Rates are physically additive across distinct phenomena, so inter-group SUM not MULTIPLY. Intra-group MAX matches the existing pattern. |
| 2026-04-26 | **Effect dict gains `kind` discriminator** (`'multiplier'` | `'rate'`) | Disambiguates `aggregate_value` interpretation. Mixed-kind groups raise `ValidationException` (a design smell). |
| 2026-04-26 | **`EnvironmentalDamage` carries `damage_type` parameter** for grouping (plasma / radiation / environmental default) | Similar to `ResourceHarvestBooster:resource_type` parameterization. Plasma + radiation become distinct effect rows in the UI; two radiation belts MAX within "EnvironmentalDamage:radiation" group. |
| 2026-04-26 | **`AreaEffectManager`, `EnvironmentalEffects`, `StormEffect` all eradicated** (per Rule 3) | Save files are disposable per CLAUDE.md System Migration Policy. No fallback / compat shims. Phase 7 grep guard verifies zero references remain. |
| 2026-04-26 | **`thrust_mult` registered in `ABILITY_STAT_REGISTRY`, combat consumption deferred** *(SUPERSEDED 2026-04-27 — see D14)* | (Original) Currently no combat code reads `thrust_mult`. Stat registration ensures storm data flows; downstream consumption is a separate small follow-up out of PROJ-300 scope. |
| 2026-04-26 | **Provider entry shape uses universal `source_kind`/`source_label`/`source_id`** instead of legacy `planet_name`/`facility_name`/`storm_name` fields | Single source-of-truth label keeps the renderer source-kind-agnostic. PROJ-301..305 add new `source_kind` values without touching the renderer. |
| 2026-04-26 | **Storm `from_dict` does NOT preserve old `effects` shape** | Save files are disposable. New saves use the `abilities` dict shape. Phase 5 rewrites the roundtrip test fixtures. |
| 2026-04-27 | **D14 — `ThrustModifier` combat consumption wired inside PROJ-300** (supersedes the 2026-04-26 "deferred" entry above) | User decision in PROJ-300..305 review: don't ship dead data. `_entries_from_sector_effects` emits a `ThrustModifier` entry per provider; combat-side stat consumption added in `game/simulation/combat/` (combat propulsion stat aggregation reads `thrust_mult`). New tests cover thrust attenuation in combat under storm + facility sources. Treat `ThrustModifier` symmetrically with `ShieldModifier` for the rest of the project. |
| 2026-04-27 | **D15 — Shared helpers `roll_intrinsic_abilities` + `format_intrinsic_source_label` ship in PROJ-300** | User decision in review: PROJ-301..304 should be pure consumers. Helpers live at `game/strategy/services/ability_sources/intrinsic_roll.py` and `.../labels.py`. Documented in design.md §Shared Helpers; tested in PROJ-300 phase_3. |
| 2026-04-27 | **D16 — Mixed-kind aggregation validates at extraction in `_aggregate`** (pinning the open question from D11) | Validates late enough to handle dynamic source kinds (PROJ-301..305), early enough to be deterministic per-call. Error message includes the contributing `source_id` + `ability_name` so the offending registry entry is identifiable from the log. |
| 2026-04-27 | **D17 — Ownerless sources may only declare ownership-neutral scopes** (`sector`, `system`) | `*_sector` / `*_system` variants on a source with `owner_id is None` raise `ValidationException` at registry load. "Enemy of whom?" is undefined for storms / planets / system archetypes. Owner-aware variants are reserved for owned sources (facilities, fleets). |
| 2026-04-27 | **D18 — Phase 6 includes a balance regression test** for the storm-stacking MAX→MULTIPLY change | Two ion storms today: `MAX(0.5, 0.5)` = 0.5×; after PROJ-300: 0.5 × 0.5 = 0.25×. New test `tests/integration/strategy/test_overlapping_storm_combat.py` asserts the multiplicative math at 1, 2, 3 overlapping storms. Pinned in phase_6_checklist. |
