| 2026-04-13 | **`SHIELD_BONUS_ADD` applies at ship-level, not per-component.** `target_attribute="max_shields"`, `base_attribute="base_max_shields"` — a single flat bonus added to `ship.max_shields` once, not cloned onto every `ShieldProjection` component. User semantic: "exactly the same as if the ship had an extra shield component providing the ability." Implementation: `Ship.recalculate_stats` reads `external_stats['shield_bonus_add']` and adds it to computed max_shields. Corrects earlier decisions.md note that suggested cloning `AbilityStatBinding` per-component. | Per-component application would scale the bonus by the number of shield generators already on the ship (ship with 2 shield gens under "+50" → +100 total), diverging from `CombatModifierCollector.flat_shield_bonus = sum(shield_projection_values)` which is a single ship-level number. User confirmed "per ship." |
| 2026-04-13 | **Pipeline ordering: `(base + flat) × mult`.** Flat shield bonus adds to base, then multiplicative effects (storm `shield_capacity_mult`, fleet `shield_mult`) scale the whole thing. Example: base 100 + flat 50 = 150 × storm 0.5 = 75 effective shields. | User-approved. Matches player intuition ("flat bonus is like adding an extra shield component, storm then weakens everything"). Locked by order of operations in `Ship.recalculate_stats`: aggregate shield capacities from all components (including ship-level flat bonus) first, then apply ship-level multipliers. |
| 2026-04-13 | **Phase 3 "suppressor routing" is scope-driven, not a separate architecture.** A "suppressor" is just a `*_mult < 1.0` with `enemy_*` scope; a "booster" is `*_mult > 1.0` with `player_*/allied_*/fleet` scope. Compiler interprets ability scope at spec-compile time: `enemy_*` routes to `per_team[opponent_id]`, else routes to `per_team[owner_team_id]`. Applies to both spec compilers. | User clarification: "the suppressor and booster effect is just the difference between multiplying by less than 1 or more than 1; the scope determines what vehicles/designs are impacted." No new data-model field needed; the existing `ability.scope` value is the routing discriminator. |
| 2026-04-13 | **Strategy compiler suppressor path already works via `CombatModifierCollector`.** Enemy-scoped abilities from opponent empire's facilities are already collected at `combat_modifier_collector.py:108-127` and rolled into the receiver-team's `FleetCombatModifiers`. Strategy compiler emits them to `per_team[receiver_team_id]` which is semantically correct for the receiver. Phase 3 for strategy compiler = verification test only. | Avoids redundant routing logic. The collector does the pre-compile work; compiler just emits what it's given. |
