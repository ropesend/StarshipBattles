| 2026-05-05 | Project initialized as PROJ-373 | Originating evidence: pyinstrument profile of 3 sequential build-queue opens (~6.9s each, ~20.6s total = 35.7% of a 58s session). Numbers in `findings/profile_summary.md`. |
| 2026-05-05 | 4-phase plan: validate cache → screen reuse → row-pool reuse → theme simplification | Each phase delivers independent measurable value (validate cache: ~2.2s/click; screen reuse: ~3-4s/click on repeat opens; row-pool: ~1.5s subset; theme: first-open + global benefit). Phases sequenced by ascending risk and decreasing isolation. Phases 1, 3, 4 are Simple; Phase 2 is Medium. |
| 2026-05-05 | Validation cache lives on `BuildQueueController` instance, not on `DesignValidator` | The validator is short-lived (constructed inside `_validate_designs`); the controller has the right lifetime, especially after Phase 2 (controller survives across opens). Could revisit if other consumers of the validator appear. Alternative B in design.md. |
| 2026-05-05 | Cache key is `(design_id, file_mtime)`, not content hash or generation counter | Mtime check is microseconds via `os.stat`, no save-side wiring required. Content hash would re-read the file every check (defeats the purpose). Generation counter is tightest but couples controller to library save path. Mtime is "good enough" — false invalidations on equal-content rewrites are harmless (re-validates, same result). |
| 2026-05-05 | Per-design cache, not per-category cache | User often toggles between categories ("Ships" → "Complexes" → "Ships"). Per-design entries survive category switches. Whole-category cache would re-validate on every toggle. Alternative C in design.md. |
| 2026-05-05 | Phase 2 is hide-then-show, not destroy-then-reconstruct | The 4.4s/click cost is in panel construction. Eliminating reconstruction is the only way to recover that cost; partial pre-baking (Phase 4b) does not avoid the UIElement hierarchy work. The architectural cost — a long-lived screen surviving across opens — is acceptable given the magnitude of the win. |
| 2026-05-05 | Panel rebuild only on context-type transition (planet ↔ fleet), not on yard switch | The factory creates different panel layouts for planet vs. fleet contexts (different context-report panel type). Same-type yard switches reuse the panel tree; cross-type transitions accept the construction cost. Cross-type transitions are rare in practice. |
| 2026-05-05 | `BuildQueueScreen` is constructed lazily on first build-yard click, NOT eagerly at app startup | Avoids paying 6.9s of construction cost during launch for users who never open the build queue. The first open in a session still pays the full cost; only subsequent opens are fast. Alternative D in design.md. |
| 2026-05-05 | Phase 2 adds new methods `BuildQueueScreen.open_for_yard(yard)`, `hide()`, `show()`, plus `BuildQueueDragHandler.reset_state()` and `BuildQueueController.reset_filters()` | Public, named lifecycle hooks beat in-place state mutation. Each method does exactly one thing and is independently testable. |
| 2026-05-05 | Phase 4 default is global theme change (`rounded_rectangle` → `rectangle`), not scoped object_id | One-line change benefits every panel-heavy screen in the game. Visual regression risk is low (3px corner radius is barely visible in dark UI). Fallback to scoped object_id (Phase 4b) only if a specific screen visibly regresses. Alternative E in design.md. |
| 2026-05-05 | Final acceptance bar: repeat-open cost < 0.5s wall-clock at baseline screen resolution | Baseline was ~6.9s; with Phase 1 + 2 + 3 each addressing distinct cost lines, sub-500ms is achievable and is the threshold at which the user perceives "instant". Verified by re-profiling. |

Scratchpad is the right home for the raw artifact. |
