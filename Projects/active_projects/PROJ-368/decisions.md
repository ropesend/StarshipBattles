| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-05-05 | Project initialized | Starting point for Strategy: OrderProcessor Decomposition (handler-per-order-type). |
| 2026-05-05 | New package name: `game/strategy/engine/order_handlers/` (not `engine/handlers/order/` and not `engine/handlers/`) | Sibling-of-handlers placement makes the parallel between command handlers (UI → order) and order handlers (action tick → state) explicit. Putting them under `handlers/` would conflate two distinct dispatchers; reusing `engine/handlers/` directly would shadow the existing `CommandHandlerRegistry`. Open Question Q5. |
| 2026-05-05 | Use a Protocol (`IOrderHandler`) and not an ABC | Mirrors `engine/handlers/base.py:84-99`'s `ICommandHandler` Protocol. Same layer, same idiom. Avoids the `interfaces/engines.py` ABC's import-graph constraints (it sits at a strategic-layer boundary that handlers should not couple to). The existing `IOrderProcessor` ABC at `interfaces/engines.py:168-230` is preserved unchanged — it's the boundary contract for `OrderProcessor`, not for individual handlers. |
| 2026-05-05 | Registry: single-handler-per-OrderType (not many-to-many like `STAT_CONTRIBUTOR_REGISTRY`) | The `OrderType → handler` relationship is exclusive. `LOAD_POPULATION`, `UNLOAD_POPULATION`, `TRANSFER` all share `TransferHandler` but the registry stores three keys pointing to the same instance. No append/replace policy needed — this isn't an extension surface like PROJ-367. |
| 2026-05-05 | Unified `OrderExecutionResult` dataclass internally; preserve `JoinFleetResult` / `ColonizeResult` / `TransferResult` / `SuperweaponResult` as backward-compat adapters at the `OrderProcessor` facade | Existing tests (1268 LOC across 4 files) assert against the typed result fields. Migrating them is risk without architectural reward. The unified type carries every field as a superset (`merged`, `cancelled`, `colonized`, `planet_name`, `amount_transferred`, plus the universal `success`/`fleet_consumed`/`message`); the facade reshapes per legacy contract. Open Question Q6. |
| 2026-05-05 | `SELF_DESTRUCT` lifted out of `superweapon_order_processor.py` into `order_handlers/self_destruct.py` (Phase 2) | `process_self_destruct` is the only superweapon `process_*` method that is **not** spec-driven via the `execute_superweapon` dispatcher (it's a 76-LOC standalone method). Lifting surfaces the asymmetry rather than papering over it with an adapter. Five adapters in Phase 4, not six. Open Question Q2. |
| 2026-05-05 | `SuperweaponOrderProcessor.process_implode_planet` / `process_stellerate_star` / `process_open_warp_point` / `process_close_warp_point` / `process_create_dyson_sphere` stay where they are; Phase 4 adds `SuperweaponHandlerAdapter` wrappers | PROJ-364 just stabilized the spec-driven pattern. Re-decomposing those 5 methods would force a re-audit of PROJ-364's invariants. Adapter pattern preserves PROJ-364's investment while giving registry-level symmetry. Open Question Q4. |
| 2026-05-05 | `process_instant_orders` adds a method to `IOrderHandler` (or is a `JoinFleetHandler`-only public method called via `isinstance`); other handlers raise `NotImplementedError` | The instant path is JOIN_FLEET-only today. Adding a Protocol method to all handlers means 4 of 5 handlers are no-ops; making it `JoinFleetHandler`-specific means the facade special-cases the dispatch. **Decision deferred to Phase 1 task 1.3** — implementer reads the code in context. Either option preserves behavior. |
| 2026-05-05 | Per-handler private state: each handler is constructed once at registry-build time with `event_bus` injected; no mutable handler state between calls | `OrderProcessor` is stateless today (only `event_bus` and `_superweapon_processor` set in `__init__`). Preserving statelessness keeps replay determinism (R5) and avoids subtle test isolation bugs. |
| 2026-05-05 | Logger names: `game.strategy.engine.order_handlers.<handler>` per module (standard `__name__` convention) | Log prefix changes from `OrderProcessor: ...` to `JoinFleetHandler: ...` etc. Documented as a public-facing log string change. No production log scraper exists. Open Question Q7. |
| 2026-05-05 | `getattr(galaxy, 'empires', [])` brittleness in `target_fleet_id` resolution preserved | Out of scope. PROJ-343 T1.1 was the historical fix at the call-site (`handlers/transfer.py:108-113`); fixing it at the resolver level is a separate concern. PROJ-368 lifts the existing logic verbatim into `TransferHandler._resolve_target_fleet_by_id` and tags it as future work in a comment. |
| 2026-05-05 | TDD discipline: every phase's first task is an existing characterization test that must pass on day 0 | `tests/unit/strategy/engine/test_order_processor_*.py` (PROJ-333 origin) is the regression guard. Phase 1 task 1.1 runs `test_order_processor_instant.py` and `test_order_processor_fleet_merge.py`; Phase 2 runs `test_order_processor_colonize.py`; Phase 3 runs `test_order_processor_transfer.py`. New per-handler tests are TDD-written **after** the handler is extracted (because the handler API doesn't exist yet on day 0 of each phase). |
| 2026-05-05 | Phase 4 is one atomic deletion-and-switchover commit | Deleting the 700+ LOC of legacy methods on `OrderProcessor` while introducing the registry switch is a single conceptual change. Splitting it across two commits would leave the codebase in an in-between state where both old and new dispatch paths exist — confusing and error-prone. R8. |
| 2026-05-05 | Reuse existing characterization test files at `tests/unit/strategy/engine/test_order_processor_*.py` as integration smoke; do not delete or migrate | Tests that drive `OrderProcessor.<method>` continue to be valid after the method becomes a delegate. They become integration tests for the facade-to-handler wiring at zero cost. New tests in `tests/unit/strategy/engine/order_handlers/` drive each handler directly. |
| 2026-05-05 | AST static guard test in Phase 5 | Locks the decomposition: future agents who add a new order type are forced into the registry pattern, not into a new `if order.type == ...` branch on `OrderProcessor`. Mirrors PROJ-273 / PROJ-278's static-guard precedent. |
| 2026-05-05 | The `IOrderProcessor` ABC at `interfaces/engines.py:168-230` is unchanged | Public boundary contract. `OrderProcessor` continues to implement it. Changing the ABC would force `MockOrderProcessor` migrations in test stubs. Out of scope for PROJ-368. |
| 2026-05-05 | Buffer depth = 0 (default) for the 03c protocol | Each phase must be `verified` before its dependent phase starts. The Phase 3 → Phase 4 boundary is the highest-risk transition (Transfer family decomposition followed by mass deletion); a verified Phase 3 before Phase 4 begins is non-negotiable. No `buffer_depth: 1` overrides. |
| 2026-05-05 | Phase dependency DAG | Phase 1 is the foundation. Phases 2 and 3 depend on Phase 1. Phase 4 depends on **both** Phase 2 and Phase 3 (it deletes methods that those phases extracted). Phase 5 depends on Phase 4. Linear with one fork-join, expressible in `phase_state.json` as: 1 → {2, 3} → 4 → 5. **Phases 2 and 3 are eligible to run in parallel after Phase 1 verifies.** |
| 2026-05-05 | Open questions surfaced in design.md, not pre-resolved | The architect intentionally lists 7 questions for the user rather than deciding unilaterally. Each question has a recommendation; user confirms or overrides. Decisions log is updated when the user resolves them. |
