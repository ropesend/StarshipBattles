# PROJ-429 Decisions Log

| Date | Decision | Rationale | Source |
|------|----------|-----------|--------|
| 2026-05-16 | **Primary registry, not view.** Implement `AbilityMetadataRegistry` as the authoritative store of strategy-layer ability metadata rather than a lazy view over an existing source. | Ability metadata has **no** upstream primary store today — facts are scattered across 11+ hardcoded literals in `game/strategy/`. PROJ-424's `OrderMetadataView` shape is appropriate for order metadata because `CommandRegistry` already exists as the primary store; that precondition does not hold for ability metadata. Building a view would force us to invent an upstream source first, then wrap it — strictly more work for no win. | TD-07 plan "Goal / End State" cross-plan note. Re-stated here so the choice is auditable from inside this project. |
| 2026-05-16 | **Keep `effect_ability_metadata.py` public helpers stable as a shim.** `EFFECT_ABILITY_METADATA`, `find_metadata`, `is_known_effect_ability`, `all_owner_aware_scopes`, and the `EffectAbilityMetadata` symbol remain importable with unchanged signatures throughout this project. Final convergence is out of scope. | Multiple downstream callers (`effect_ability_display.py`, `system_effects_collector.py` consumer chains, etc.) import these names directly. Breaking that API mid-flight would multiply the touch surface and spread the change across consumers TD-07 explicitly excludes. The shim isolates the migration; collapsing the shim is a follow-up project. | TD-07 plan "Weak-LLM Guardrails" and "Acceptance Criteria" item 2. |
| 2026-05-16 | **Migrate one consumer per phase.** Phases are deliberately small and sequential: each one migrates a single consumer (or a single closely-paired pair like `combat_modifier_collector` + `spec_compiler` in Phase 5), keeps the public test surface of that consumer green, and exits clean. | TD-07's remediation plan is explicit about strict TDD with one consumer at a time so intermediate states are green. Parallelization across phases is not safe here — the registry's tag set grows as each consumer is migrated, and a multi-consumer phase would risk landing partial tag taxonomies. | TD-07 plan "Remediation Plan" preamble. |
| 2026-05-16 | **`ShieldProjection` gets a distinct kind tag (`COMBAT_FLAT_BONUS`), not `COMBAT_MODIFIER`.** | `ShieldProjection` accumulates as a flat bonus (`combat_modifier_collector.py:109,113`), not via the multiplier aggregation path used for `ShieldModifier`/`DamageModifier`/`ThrustModifier`. Lumping it with `COMBAT_MODIFIER` would route it through `aggregate_multipliers` and change behavior. A separate kind tag makes the categorization honest and preserves the existing aggregation path. | TD-07 plan "Weak-LLM Guardrails" and "Risks" table row on `ShieldProjection`. |
| 2026-05-16 | **Delete `_ACTIVATABLE_ABILITIES` rather than fix it.** | The constant at `planet_energy_engine.py:80-89` is dead code (verified — no in-file reads, no external imports beyond docs). The live drain path at lines 270-282 already reads `ComponentActivationState.is_draining_energy`. CLAUDE.md rule 3 mandates root-cause fixes, not compatibility shims around inert state. | TD-07 Verification Findings, "Dead code surfaced during verification" section. |
| 2026-05-16 | **Do not collapse `StabilizerSpec` / `SuperweaponSpec` into the unified registry in this project.** Phase 6 adds only contract tests proving their `ability_name` fields are tagged correctly. | Both specs own operation-specific data (scopes, blocks, target_type, consume_ship, event_type) that is not generic ability metadata. Collapsing them in this project would broaden scope beyond categorization and risk regressions in superweapon dispatch / stabilizer order-blocking. Full convergence is a follow-up. | TD-07 plan "Weak-LLM Guardrails" item: "Do not collapse `StabilizerSpec` or `SuperweaponSpec` into the new registry in this plan." |
| 2026-05-16 | **Registry is a leaf — no imports from `game/simulation/`.** Ability names are strings; metadata is pure data. | Prevents an import cycle between the simulation layer (where abilities live) and the strategy layer (where this registry lives). The registry's job is categorization, not instantiation. | TD-07 plan "Risks & Mitigations" first row. |
| 2026-05-16 | **Hard dependency on PROJ-424 (TD-03) is project-level, not phase-level.** Phase 0 does not start until PROJ-424 is verified-and-merged. | TD-03 reshapes `CommandRegistry`'s exposed API via `OrderMetadataView`. Phase 4 here reads that API. Starting any phase of PROJ-429 before PROJ-424 lands risks (a) re-implementing the view-layer interaction mid-flight, or (b) leaving Phase 4's `ORDER_TO_TIME_FIELD` collapse half-done. The EXECUTION_ORDER doc encodes the same edge: `TD-03 -> TD-07`. | TD-07 plan "Dependencies / Order" and `EXECUTION_ORDER.md` "Phase Gates" rule 4. |
