| 2026-05-16 | Replace `object.__setattr__(spec, ...)` side channels with a typed `BattleSpecExtensions` dataclass on a `StrategyBattleAssembly` wrapper | `BattleSpec` is a frozen `simulation`-layer DTO that must remain unmutated post-construction. The four current side-channels (`_mine_groups`, `_owner_to_team_id`, `_engine_ref`, `_combat_fleets`) are strategy-only state that has no business living on the simulation DTO. A typed sidecar makes the extension seam explicit, allows future strategy-state-affects-mid-battle-behavior features to add fields without touching `BattleSpec`, and removes the "stash in private attr, fish it back out in the adapter" pattern that has already grown from 3 attrs to 4. |
| 2026-05-16 | Split the spec compiler into named builders (`StrategyBattleAssembler`, `TeamSpecBuilder`, `StrategyModifierStackBuilder`, `PostBattleHookBuilder`, `PreTickBattleSetupRegistry`) instead of leaving one large function | `build_strategy_battle_spec(...)` is a single 200-line function doing 8 unrelated things (mine split, team grouping, modifier translation, boundary resolution, end-condition picking, post-battle hook construction, side-channel mutation) plus the file also hosts two unrelated pre-tick setup builders. Named builders create explicit extension seams, let unit tests target each concern in isolation, and bring every file comfortably under the 500-LOC ceiling. |
| 2026-05-16 | Preserve the public import path `game.strategy.combat.spec_compiler.build_strategy_battle_spec` for this remediation | Many tests and docs import it directly; deleting/renaming the module adds churn without reducing underlying debt. `spec_compiler.py` shrinks to a thin facade (`<= 120 LOC`) that instantiates the assembler and returns `assembly.spec`. This is the public seam, **not** a fallback shim in the AGENTS.md sense. |
| 2026-05-16 | Migrate tests that assert on private side-channel attribute names or private helpers in the **same phase** as the seam change — no compatibility shims | AGENTS.md root-cause rule. Specifically: (a) `tests/unit/strategy/combat/test_fighter_group_combat_join.py` and `test_satellite_group_combat_join.py` import `_split_mine_groups_from_fleets`; both migrate to `TeamSpecBuilder` in Phase 2 and `spec_compiler.py` does **not** re-export the old helper. (b) `tests/integration/test_fms_b_e2e.py:414, 415, 420, 493` reach into `spec._mine_groups` and `spec._owner_to_team_id`; migrated to `assembly.extensions.*` in Phase 4 **before** the `object.__setattr__` writes are deleted. |
| 2026-05-16 | Phase 4 deletion of `object.__setattr__(spec, ...)` writes is gated on adapter + test migration landing first | Reverses an obvious failure mode: deleting the writes before the readers are migrated leaves the tree red. The phase checklist enforces ordering (migrate adapter; migrate three test files; only then delete the four writes). |
| 2026-05-16 | Keep `BattleSpec` frozen and do **not** add fields to `game/simulation/battle_spec.py` | Source plan executor guardrail: extra strategy-only state belongs beside the spec, not on the frozen simulation DTO. Adding fields would be a layer violation (strategy concerns leaking into `game/simulation/`). The typed sidecar pattern (`BattleSpecExtensions`) is the canonical answer. |
| 2026-05-16 | `BattleSpecExtensions.engine_ref` stays a mutable one-slot list inside an otherwise frozen dataclass | The pre-tick callback fills this slot with the `BattleEngine` instance at battle start so the post-battle hook can call `apply_reboard`. Mutation is required by the runtime contract; only the storage location changes. The frozen dataclass holds the list reference; the list itself is mutable. |
| 2026-05-16 | `StrategyBattleAssembler` will carry a `mine_group_filter` parameter that PROJ-431 Phase 2 simplifies away — do NOT pre-collapse it here | Intentional handoff to PROJ-431 (TD-10 deployable substrate redesign). Once deployables (mines, satellites, fighter groups) live on a unified substrate, the mine-specific filter is no longer needed. Collapsing it inside this project would couple TD-01 and TD-10 and force one of them to do work that belongs to the other. EXECUTION_ORDER.md gates TD-10's main redesign behind this project's completion specifically because of this kind of seam-design coordination. |
| 2026-05-16 | Move `build_mine_resolver_setup` and `build_fighter_reboard_setup` out of `spec_compiler.py` into a `game/strategy/combat/pre_tick_setup/` package owned by `PreTickBattleSetupRegistry` (Phase 3) | These two unrelated pre-tick setup builders currently co-habit the spec-compiler module (`spec_compiler.py:454-549`) — they're imported by the adapter, not the compiler itself, so their presence in this file is a kitchen-sink artifact. A named registry with deterministic composition order makes the "pre-tick setup" extension point explicit, lets future setups (e.g., environmental hazard initialization) register without touching the compiler, and removes ~95 LOC from `spec_compiler.py`. |
| 2026-05-16 | Phase 0 is read-only baseline capture (no code edits) | Source plan's preflight phase. Re-run the two `rg` commands from Executor Guardrails immediately before code work, since parallel projects could have added a 5th side-channel attr. The verification step already found one attr the original report missed (`_combat_fleets`); assume the touch list can drift. |
