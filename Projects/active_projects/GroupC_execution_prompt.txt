## Per-project workflow (apply to each of the 4 projects)
================================================================================

### Step 1 — Pre-project orientation

- Run `python Projects/scripts/current_task.py PROJ-XXX` to see the live current state.
- `git fetch origin main` — keep your view of cross-group state current.
- Read the plan.md "Current State" block + "Group C execution context" block in Dependencies.
- Confirm the serial gate (predecessor project is complete OR you are PROJ-452 starting the chain).
- Read the next-pending phase checklist in full.

### Step 2 — Execute each phase

For each phase from first to last:

- Open `phase_N_checklist.md`. Read in full before starting any task.
- Execute tasks in the listed order unless a task's "Notes" explicitly allows reordering.
- Use the TDD pattern the project documents:
  - **PROJ-452** — RED-then-GREEN. Each Phase has a new failing test before the fix.
  - **PROJ-455** — Characterization-first (test-only coverage project). Phase 1 establishes the fixture; Phase 2 lands the parametrized test (Task 2.1 = completion branch + Task 2.4 = in-progress branch, BOTH required per `phase_2_checklist.md`'s Phase Completion Checklist); Phase 3 updates the DI log.
  - **PROJ-458** — RED-then-GREEN per window. Each phase: new dedicated characterization tests against the bypass-init shell first (RED), then apply the two-stage retrofit (GREEN).
  - **PROJ-460** — Characterization-first refactor. Each phase has the round-trip test landing GREEN against current code (it's a structural extraction, not a behavior change); the gate is "post-extraction round-trip still GREEN".
- Run targeted pytest after each task (the checklist tells you which file).
- At the end of each phase: run `python Tools/test_sharded/test_sharded.py` (full sharded suite). If RED, apply the flake-retry protocol per §13 (isolate failing tests; if all pass alone, retry sharded once; STOP only on second consecutive RED). Note any flake retry in the commit message.
- **PROJ-460 Phase 1, Phase 2, and Phase 3 extra gate**: ALSO run `pytest tests/integration/replay/ tests/integration/save_load/ -v`. These are the critical automated regression gates for replay/serde + battle-controller spec-in work; do not declare these phases complete without them green. (This replaces the prior manual UI smoke test gate on Phase 2 — automated coverage is now the contract.) The flake-retry protocol also applies to these targeted suites.
- Mark task checkboxes `[x]` as you go.
- Update plan.md "Current State" block whenever you pause (Last Updated date; Active Phase; Last Action; Next Action; Blockers).

### Step 3 — Phase completion gate

For each phase:
- All task checkboxes in `phase_N_checklist.md` are `[x]`
- Targeted tests green
- Sharded suite green
- Replay/save-load suite green (PROJ-460 Phase 1, 2, 3)
- `python Projects/scripts/validate_phase.py PROJ-XXX N` reports PASSED
- Update `phase_N_checklist.md` Status: → `Complete`
- Update `plan.md` Quick Status table row N → `Complete`
- Update `plan.md` Current State → next phase OR project-complete
- **Commit + push on `group-c`**: `PROJ-XXX Phase N: <description>` then `git push origin group-c`
- **Checkpoint summary** (per protocol §15.2): if you have just completed your 3rd phase since the last checkpoint, OR if this is a project boundary (start or end), append a Checkpoint Log entry in plan.md (create the `## Checkpoint Log` section on first write). Target ≤200 words: Done so far / Key decisions / Open threads / Next action / Cross-group state observed at last `git fetch origin main`. Commit + push with the next phase commit.

### Step 4 — End-of-project codex audit (MANDATORY after every project)

After ALL phases of a project are complete:

1. Dispatch a codex consult auditing the just-completed project. Consult location (per protocol §10) is **under the audited project**:

   `Projects/active_projects/PROJ-XXX/consults/<UTC-ts>_end-of-project-audit/`

   This is tracked per-project (visible cross-machine after push), not the old gitignored Scratchpad location. Reference templates from the prior per-bucket audits (older artifacts may live under `AgentCoordination/Scratchpad/Consult/` and may not be present on your local checkout):
   - Bucket B audit (covered PROJ-452 + PROJ-455 originally): `20260519T014918Z_audit-bucket-B-engine-services/`
   - Bucket C audit (covered PROJ-458 originally): `20260519T014918Z_audit-bucket-C-ui-cluster/`
   - Bucket D audit (covered PROJ-460 originally): `20260519T014918Z_audit-bucket-D-loc-extractions/`

2. Audit consult brief (per project):
   - Scope: just the one project that just completed
   - allow_tests: false
   - Ask codex to verify: (a) all phase checklists actually closed correctly, (b) the production code changes match what the plan documented, (c) no behavior regressions visible in the diff, (d) no new discovered_issues that should be logged, (e) the project's verification checklist gates are all met.
   - Output: per-project response.md in the new consult leaf.

3. Invocation: use the reference pattern in protocol §10.1 — discover `REPO_ROOT` at runtime, invoke `partner_invoke.py` from `<REPO_ROOT>/Tools/agent_coordination/`. Do NOT hardcode any checkout path.

4. Read codex's response.md. **If the response is long (>300 lines)**: per protocol §15.1, spawn a `general-purpose` subagent with the response.md path. Brief: "Summarize codex's response in ≤300 words; list verified issues, false positives, and out-of-scope items separately. Each verified issue: file:line + one-sentence rationale." Read the subagent's summary in main context, then use Read selectively on the response for the items you act on. Commit the consult leaf on `group-c` and push.

5. **If codex flags VERIFIED issues** (test the claim — read the file/line codex cites before treating it as real):
   - For each verified issue, create a NEW PHASE in the same project addressing it.
   - Phase numbering: continue from the last phase (e.g., if Phase 5 was the original last, new audit-driven phases start at Phase 6).
   - Update the plan.md Quick Status table to add the new phases.
   - Update Current State to point at the new phase.
   - Execute the new phase using the same workflow above (commit + push per phase).
   - Repeat the codex audit if the new phases are non-trivial (>30 LOC of production change).

6. **If codex's findings are over-stated or wrong** (you verified, found the claim doesn't hold): document the false-positive in `decisions.md` with evidence and move on. Do not create a phase for it.

7. **If codex's findings are truly new but out-of-scope** (legitimate issue but outside this project's job): log via `/claude-di-log` so it lands in `AgentCoordination/discovered_issues/log.jsonl`, then move on.

8. Only after all codex-verified issues are addressed AND the new phases close green should you proceed to Step 5 (end-of-project merge).

### Step 5 — End-of-project merge to `main` (per protocol §3)
