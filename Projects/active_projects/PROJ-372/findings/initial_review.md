## PROJ-370 sequencing recommendation

**Recommendation: PROJ-372 ships first, independently.**

### Reasoning

1. **PROJ-370 is currently a 1-phase stub.** Its `plan.md` has the boilerplate "TBD" for Phase 1; `design.md` has placeholder `[Risk/Dependency]`. Holding PROJ-372 on a project that hasn't planned itself is risky.
2. **PROJ-372 produces useful inputs to PROJ-370.** Phase 0 of PROJ-372 introduces 5 read protocols — `IGalaxySystemGraph`, `IGalaxySpatialQuery`, `IHabitabilityCalculator`, `IStockpileHolder`, `IStagingYardHolder` — which are exactly the kind of typed surface PROJ-370 will layer contract tests over.
3. **Scope separation is clean.** PROJ-372 is "extract god-class internals into services"; PROJ-370 is "enforce invariants at write sites". They share data classes but operate on different concerns.
4. **No structural conflict.** PROJ-370's likely targets (Fleet.resources, Planet population/stockpile mutation paths) don't overlap with PROJ-372's god-class surgery; PROJ-372 leaves the public mutation API on `Planet` exactly as-is (per Risk R8 in design.md).

### What if PROJ-370 ships first?

PROJ-372 would gain: a defined `IFleetResourceManager` / `IPlanetManager` from PROJ-370 to consume directly instead of inventing the smaller `IStockpileHolder` / `IStagingYardHolder`.
PROJ-372 would lose: nothing of substance — its protocol surface is a strict subset of PROJ-370's likely scope. The duplication would be ~30 LOC of protocol definitions that PROJ-370 could re-export.

### What if they ship in parallel?

Possible if both teams coordinate on the 5 protocol names. Risk of churn if PROJ-370 renames or restructures protocols mid-flight.

### Final answer

**PROJ-372 first.** Less risk, useful intermediate output, no scope conflict.

## Top 5 surprises

### 1. Facade pattern is already 50% in place on Galaxy

Of `Galaxy`'s 31 methods, **16 are already 1-line facades** to PROJ-173-Phase-2 delegates (`_registry`, `_spatial`, `_warp_gen`, `_sys_gen`). The work isn't "introduce the facade pattern" — it's "finish what PROJ-173 started + extract the remaining 8 logic-bearing methods + introduce `GalaxyState` to break the `_galaxy: Galaxy` back-reference on the four delegates."

### 2. `Planet` is mostly already a dataclass — the LOC pressure is from save serde, not logic

`Planet` is 667 LOC. Of those, **179 are `to_dict` (60) + `from_dict` (119)** — 27% of the file is just save/load handling for 47 fields. Removing the 4 logic-bearing query methods saves ~40 LOC; the remaining ~290 LOC is dataclass fields + identity + 11 small mutation methods + serde, which is intrinsic. `≤ 350 LOC` target is achievable but tight.

### 3. `stars.py` is 770 LOC because three classes share one file, not because any one class is bloated

`Star` is 120 LOC, `Spectrum` is 70 LOC, `StarGenerator` is 517 LOC, math constants are 35 LOC. Four files at 280 / 80 / 500 / 200 LOC each is just splitting along well-known seams; no one class is god-sized. The "770 LOC god class" framing in the source review is misleading. **The file is the god, not any class within it.**

### 4. Habitability cache on Planet is already correctly designed (PROJ-285)

`Planet._cached_habitability_multiplier` and `_cached_multiplier_turn` use `init=False, repr=False, compare=False` and are NOT serialized. The cache invalidates on turn change. The only thing missing is **swappable calculator** — and that's a 1-line refactor: replace the late-imported `planet_habitability_multiplier(...)` call with a service call. The facade goal (G4) is much smaller than the source review implied.

### 5. Pathfinding has 82 callers across 15 files

`pathfinding.py`'s 8 free functions are called from 82 sites across 15 files (verified via grep). This is the largest blast radius in PROJ-372 — Phase 4's deprecated-shim approach (1-line wrappers + `DeprecationWarning`) is essential for a clean migration; deleting the shims at Phase 5 close requires Task 5.1's exhaustive sweep first. **Plan ≥ 1 day of buffer for the migration sweep.**
