### `StarAbilitySource` adapter

```python
@dataclass(frozen=True)
class StarAbilitySource:
    star: Star
    system: StarSystem  # parent system, captured at adapter construction

    @property
    def source_kind(self) -> str:
        return 'star'

    @property
    def source_label(self) -> str:
        return f"{self.star.name} ({self._type_label})"

    @property
    def source_id(self) -> str:
        return f"star:{self.star.id}"

    @property
    def owner_id(self) -> Optional[int]:
        return None

    def get_abilities(self) -> Dict[str, Any]:
        return self.star.intrinsic_abilities

    def affects_hex(self, hex_coord) -> bool:
        # Stars project sector-scope abilities only at the star's own hex.
        # System-scope abilities are not gated by affects_hex (they're picked
        # up by the system iterator). The hex iterator filters at the scope
        # level via _SECTOR_SCOPES.
        star_global = self.system.global_location + self.star.location
        return hex_coord == star_global

    def affects_system(self, system) -> bool:
        return system is self.system
```

### Iterator registration

```python
def _star_provider_at_hex(system, hex_coord):
    for star in system.stars:
        source = StarAbilitySource(star, system)
        if source.get_abilities():
            yield source

def _star_provider_in_system(system):
    for star in system.stars:
        source = StarAbilitySource(star, system)
        if source.get_abilities():
            yield source

# Register both — at-hex provider also yields system-scope sources
# (the collector filters by scope, so a star with only system-scope
# abilities yields zero matches at non-star hexes — correct behavior).
register_source_provider_at_hex(_star_provider_at_hex)
register_source_provider_in_system(_star_provider_in_system)
```

(PROJ-300's iterator already supports both registration kinds; adapt the actual API names to what landed.)

### Key Patterns to Reuse

### Dependencies & Risks
1. **`star_type` taxonomy alignment** — registry must match the actual generated star types. Add a coverage validation test like PROJ-301.
2. **System-scope filtering** — confirm PROJ-300's `_aggregate` correctly filters system vs sector scope when ownerless sources are included. Tests should cover all four cases (system source × system query, system source × sector query → not picked up unless at star's hex with sector scope, etc.).
3. **Pulsar's `ShieldModifier scope: system`** is a meaningful combat behavior change — every battle in a pulsar system gets stacked shield reduction with whatever facilities project. Confirm this is the intent before generating production data.

### Opportunities Discovered
- The system × sector scope distinction is exercised more thoroughly here than in PROJ-300/301. Tests written here strengthen the framework's invariants for PROJ-303 (warp points) and PROJ-304 (system archetypes) which also span both scopes.
