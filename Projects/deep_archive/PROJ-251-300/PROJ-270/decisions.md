## Locked Architectural Decisions (established during planning)

| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-04-12 | Project initialized as continuation of PROJ-269 | PROJ-269 declared "implementation complete" but independent audit found 5 live production bypasses of `run_battle`, System Migration Policy violations on scenario templates, and a gameplay regression (placeholder stat_keys) nobody was tracking. PROJ-270 exists to close those gaps. |
| 2026-04-12 | **Strategic-modifier battle-math restoration IS IN SCOPE for PROJ-270, with an explicit bounded trim point.** Phase 6 maps only the 1:1 multiplier sources (storm `shield_capacity_mult`, fleet `shield_mult` → `shield_capacity_mult`, fleet `damage_mult` → `damage_mult`). Flat-shield-bonus (needs new `SHIELD_BONUS_ADD` additive stat_key) and suppressor effects (need opponent-team routing) are deferred to PROJ-271 if Phase 6 exceeds 3 implementation days. | The regression is a real gameplay change (pre-PROJ-269 these effects applied to ship stats; post-PROJ-269 they do nothing). Leaving it as an orphaned TODO is how regressions become permanent. Bounding the scope keeps PROJ-270 closeable; the trim point gives the implementer a pressure-valve if discovery reveals hidden work. Battle-math audit agent estimated 20–35 engineer hours for the full scope — PROJ-270 targets the fast 8–10 hour subset. |
| 2026-04-12 | **Visual-mode approach: `BattleController` becomes a spec-consuming per-frame adapter that emits `BattleOutcome` at battle end.** Visual mode does NOT call `run_battle` directly (blocking). Instead: `BattleController.configure(spec)` calls `start_engine_from_spec(spec, ...)` internally, the UI drives `BattleController.update()` per-frame, and `BattleController` calls `extract_outcome(engine, spec)` in its end-of-battle handler. `BattleResultsScreen` reads the outcome. | Rewriting visual mode to drive `BattleEngine` directly would require either a non-blocking `run_battle` variant (large refactor) or a generator-based `run_battle_ticks(spec)` (new API surface). The spec-in / outcome-out contract is honoured while preserving the UI's per-frame shape. `materialize_spec_ships` (already shared today) becomes the single materialization path. |
| 2026-04-12 | **Acceptance criterion for "every battle enters via `run_battle(spec)`":** (a) zero direct `engine.start*()` calls outside `run_battle`, `start_engine_from_spec`, `BattleService.create_battle`, and `BattleController` lifecycle methods; (b) zero `BattleEngine(...)` constructions outside `start_engine_from_spec` and `BattleService.create_battle`; (c) every live production battle produces a `BattleOutcome` (headless, visual, Combat Lab, Battle Setup, strategy); (d) zero `setup(battle_engine)` methods remaining on scenario templates; (e) zero `"Legacy-compatible"` / `"retained for"` / `"deprecated"` comments in live code under `combat_lab/`, `game/simulation/`, `game/ui/`. | Enforceable via a grep-based audit task (Phase 8.3) and a pytest guard test that fails if any forbidden symbol re-enters the live codebase. This criterion is objective, auditable, and prevents silent regression of the unified-entry contract in future work. |
| 2026-04-12 | **Combat Lab outcome adoption (Phase 2) MUST land before visual-mode outcome adoption (Phase 4).** Phase ordering is dependency-driven, not preference-driven. | Audit finding New-A: visual-mode cannot adopt `BattleOutcome` cleanly until the outcome-consumption pattern is proven against 162 Combat Lab scenarios. If Phase 4 ran first, there would be no reference for what fields the outcome must carry and how to consume them. Phase 2 is the pattern; Phase 4 is the application. |
| 2026-04-12 | **Combat Lab forensic telemetry (in-flight projectile counts, per-tick position tracks) handled via Option B — returned as a `CombatLabTelemetry` bundle from a Combat Lab-specific helper, NOT extended onto simulation-layer `BattleOutcome`.** Alternative (Option A: extend `BattleOutcome` at DETAILED level) was considered and rejected. | Option A would leak Combat-Lab-specific forensic data into the simulation DTO — a layer violation. `BattleOutcome` is imported by strategy and UI layers that have no need for projectile tracks. Option B keeps simulation-layer DTOs lean while giving Combat Lab its forensic surface. Final shape determined in Phase 2 Task 2.1. |
| 2026-04-12 | **PROJ-269 is NOT moved to `archived_projects/` until its manual launcher smoke + project audit complete.** PROJ-270 proceeds in parallel with PROJ-269's outstanding manual-smoke step. The two projects' working trees do not conflict. | PROJ-269's automated deliverables are landed (verified by audit). Its outstanding items (manual launcher smoke + protocol 04 audit) are interactive-only and do not block PROJ-270's code work. Splitting archival from closure avoids coupling PROJ-270's implementation timeline to a human-dependent step. |
| 2026-04-12 | **Deletion of stub modules (`battle_factories.py`, `battle_mode_handler.py`) happens in Phase 8.2, not earlier.** | These stubs contain only `DELETED in PROJ-269 Phase 6` docstrings.
