# BUG-125: Hot-seat — drop Command.empire_id + fix session.active_empire rotation; planet + fleet command handlers gate correctly

## Description

In a multi-empire (hot-seat) game, the active player can select and
issue orders to fleets belonging to OTHER empires. The user expects
the same ownership gating that already applies to colonies — you can
only command what you own.

User commentary at QA Session 20260428_190154 [19:11:52]:
> "You should only be able to give orders to your fleets and you should
> only be able to control your colonies. It appears that you can give
> orders to the other player's fleets."

## Code investigation findings

**Colony commands gate correctly.** `IssuePlanetOrderCommandHandler`
([`game/strategy/engine/handlers/planet_command_handlers.py:47`](../../../game/strategy/engine/handlers/planet_command_handlers.py#L47))
verifies `planet.owner_id != session.player_empire.id` before issuing
the order. Same gate is present in
`ClearPlanetOrdersCommandHandler` (line 110) and
`DeletePlanetOrderCommandHandler` (line 128).

**Fleet commands do not.** The fleet handlers in
[`game/strategy/engine/handlers/movement.py`](../../../game/strategy/engine/handlers/movement.py)
trust the UI-supplied `cmd.empire_id` parameter:

- [`MoveCommandHandler` line 75](../../../game/strategy/engine/handlers/movement.py#L75)
  resolves the fleet via `_resolve_fleet(session, cmd.fleet_id,
  empire_id=cmd.empire_id)`. The check passes whenever the UI sends
  the fleet's actual owner_id — which it does, because the UI dispatches
  via `FleetOperations.execute_move(...)` and pulls `empire_id =
  fleet.owner_id` from the selected fleet rather than from
  `current_empire.id`.

- [`InterceptCommandHandler` line 109](../../../game/strategy/engine/handlers/movement.py#L109)
  validates source-fleet ownership via the same UI-trusted
  `cmd.empire_id`. **Worse: target fleet is resolved at line 117
  without any empire_id at all** — `_resolve_fleet(session,
  cmd.target_fleet_id)` — so any fleet can be made the intercept
  target regardless of ownership.

- [`JoinCommandHandler` line 139](../../../game/strategy/engine/handlers/movement.py#L139)
  blocks *cross-empire* joins (`fleet.owner_id != target_fleet.owner_id`
  at line 156) but still trusts `cmd.empire_id` for the source.

**No central ownership-check utility exists.** Inline checks,
inconsistent between fleet and colony paths.

## Root cause

The UI dispatch path (`FleetOperations.execute_*` →
`Issue*Command(empire_id=fleet.owner_id, ...)`) sets `empire_id` from
the *selected fleet's owner*, not from the *active player*. Then the
handler validates that the command's `empire_id` matches the fleet's
`owner_id` — a tautology (`fleet.owner_id == fleet.owner_id`) that
authorises any selectable fleet.

The handler must validate against
`session.player_empire.id` (or the equivalent active-player accessor),
not against a UI-supplied parameter.

## Proposed fix path (not prescriptive)

1. **Tighten the contract.** Either:
   - Drop `empire_id` from the fleet command DTOs entirely and have
     handlers read `session.player_empire.id` directly (matching the
     planet-handler pattern), OR
   - Keep `empire_id` on the DTO but validate in the handler that
     `cmd.empire_id == session.player_empire.id` AND
     `cmd.empire_id == fleet.owner_id`.
   The first option is cleaner — single source of truth for "who is
   acting" — and matches the planet-command convention.

2. **Add ownership check on intercept target.** The
   `target_fleet_id` resolution at `movement.py:117` must also gate
   against the player. Decide the policy: probably "you can intercept
   any fleet you can see, but the order must be issued by your own
   fleet only" — so the *source* fleet ownership is the gate, target
   ownership is allowed.

3. **Extract the ownership pattern.** Add a small helper
   `_require_player_fleet(session, fleet_id) → Fleet` that loads the
   fleet, raises a clear command-rejected error if
   `fleet.owner_id != session.player_empire.id`, and is used by every
   fleet handler. Mirror the colony pattern.

4. **UI hardening.** `StrategyClickDispatcher` / `FleetOperations`
   should not even let the player *select* an opponent's fleet for
   command issuance. Add a `fleet.owner_id == current_empire.id`
   guard in the click handler to short-circuit before any command
   is dispatched. (Defence in depth — handler still gates server-side.)

5. **Tests.**
   - `tests/integration/strategy/test_fleet_command_authorization.py`
     (new) — assert that issuing `MoveCommand` / `InterceptCommand` /
     `JoinCommand` against an opponent's fleet raises a command-
     rejected error or no-ops.
   - Add an existing-suite check that the planet handlers still
     reject opponent-planet orders (regression coverage).

## Acceptance

- A player in hot-seat mode cannot move, intercept, or join an
  opponent's fleet — clicking the fleet either does nothing
  (UI gate) or the command is silently rejected (server gate).
- All existing single-empire fleet-command tests still pass.
- A new integration test demonstrates the rejection of cross-empire
  fleet orders.

## Priority

High — multi-empire (hot-seat) play is unplayable as a fair
competitive mode while one player can move the other player's
ships. Same severity class as BUG-123 (event log leaks) — both are
multi-empire correctness bugs.

  Code investigation during triage isolated the trust boundary

- 2026-04-29: **Investigation expanded scope.** Deep-dive
  investigation found two compounding bugs and 25 affected fleet
  handler call sites (not the 5 the original triage identified):
  1. UI dispatch passed `cmd.empire_id=fleet.owner_id` and the
     handler gated against `cmd.empire_id == fleet.owner_id` (a
     tautology) — trusting UI-supplied identity.
  2. `session.player_empire` was set ONCE at session create to
     `empires[0]` and **never rotated** in hot-seat. Planet command
     handlers (cited in the original ticket as "the right pattern
     to copy") were silently broken in hot-seat for player 2 — the
     gate compared against the stale `player_empire`. Triage missed
     this because single-player and player-1's-turn-in-hot-seat
     happen to coincide with `empires[0]`, so the symptom was
     invisible until rotation.

  **Resolution (Q5=DROP, Option A per CLAUDE.md System Migration
  Policy):**
  - Dropped `Command.empire_id` field from all DTOs. Identity is
    session context, not request body. Migrated ~30 test sites
    that passed the kwarg.
  - Renamed `session.player_empire` → `session.active_empire`.
    `StrategyGameStateManager.advance_turn._sync_active_empire`
    pushes the rotation into the session each turn change. All 8
    production reads of `session.player_empire` migrated; the
    rename also clarifies semantics (no reader wanted "original
    creator", confirmed via exhaustive grep).
  - Added `BaseCommandHandler._resolve_player_fleet(session, fleet_id)`
    helper. All 6 fleet handler files (movement, transfer, build,
    order_queue, superweapon_command_handlers + base) now use it
    for source-fleet authorization. Lower-level
    `_resolve_fleet(empire_id=None)` retained for the legitimate
    cross-empire intercept-target lookup.
  - Planet command handlers continue to gate on
    `session.active_empire.id` inline — the rename makes that gate
    correct in hot-seat (auto-fix bonus from RC#2).
  - All 11 UI dispatch sites no longer pass `empire_id=`.
  - `strategy_screen.py` L307 and L343 ungated `selected_fleet =
    fleet` assignments now check
    `fleet.owner_id == session.active_empire.id` first.
