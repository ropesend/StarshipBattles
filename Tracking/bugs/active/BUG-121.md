# BUG-121: Strategy screen mouse-wheel zoom does not work

## Description
On the strategy screen (galaxy / system map view), the mouse scroll wheel
no longer zooms the camera. Other zoom paths (if any keyboard or button
shortcuts exist) are not affected by this report — the user specifically
calls out the scroll wheel.

Reported in QA Session 20260427_151244 at 15:55 (no screenshot — the
behaviour is the absence of zoom on wheel input).

A complementary keyboard fallback (numpad `+` / `-`) is being added in
parallel as **FEAT-21** so the user can keep functioning while this bug is
investigated.

## Suspected Cause
`StrategyInputHandler._handle_scroll()`
(`game/ui/screens/strategy_input_handler.py:160-182`) early-returns when
`self.scene.ui._has_modal_open()` is True (line 175 region). This is the most
likely place the wheel event is being swallowed before it reaches the camera.

Hypotheses for next investigator:
1. A panel (planet list, fleet report, build queue, etc.) is reporting
   `_has_modal_open == True` even when it is not visually modal — check
   `strategy_window_manager.py` and the windows it tracks for stale modal
   flags.
2. A recently-added window subscribes to the modal stack but never
   deregisters when closed/minimised.
3. The camera's `update_input` event filter at line 197
   (`cam_events = [e for e in events if e.type != pygame.MOUSEWHEEL]`) is
   correct, but if step 1 is broken the wheel event never enters the path
   that finally reaches the camera.

## Reproduction
1. Open a save with the galaxy view loaded.
2. Hover over the map (not over any sidebar/window/topbar).
3. Scroll the wheel.
4. Expected: camera zooms in/out.
5. Actual: nothing happens.

## Suggested Fix Path
Add temporary logging to `_handle_scroll`: log the result of
`_has_modal_open()` and which window claims to be modal at the time of the
event. Capture from the user's repro session. Once the offending panel is
identified, fix its modal-flag lifecycle.

### Root Cause
`StrategyWindowManager.planet_abilities_window` was a stale-flag leak.
PROJ-309 sub-phase 3.10 added the slot to
`StrategyEventRouter.has_modal_open()` and `_is_blocking_ui_element_at()`
(read side) but did NOT add the close-side cleanup. Unlike every other
modal-tracked slot — which clears either via
`StrategyEventRouter._handle_window_close` (13 slots) or via a registrar
`on_close_callback` fired from the window's overridden `kill()` (e.g.
`planet_list_window` / `PlanetListRegistrar._on_closed`) — `PlanetAbilities`
had neither mechanism: no `kill()` override on the window, no `_handle_window_close`
branch, no `on_close_callback` registered by the registrar.

Effect: once the user opened the Planet Abilities window (Abilities button
on the planet sidebar) and closed it via the "X", pygame_gui killed the
window but `wm.planet_abilities_window` kept pointing at the dead UIWindow.
`has_modal_open()` checks `is not None`, not `.alive()`, so it returned
True permanently. `_handle_scroll` then short-circuited every subsequent
wheel event for the rest of the session.

Same bug class as BUG-69 (`fleet_orders_window` / `fleet_report_window` /
`transfer_dialog` close handlers wired up incorrectly) and BUG-22
(`planet_list_window` originally absent from `_has_modal_open` scan).

Asymmetry note: `StrategyEventRouter._is_blocking_ui_element_at` correctly
checks `window.alive() and window.rect.collidepoint(...)`, which is why
clicks kept working but scroll did not. Unifying these two paths (either
both check `is not None` with a guarantee that slots clear on kill, OR
both check `.alive()`) is out of scope for this fix and tracked below as a
follow-up suggestion.

### Fix
1. `game/ui/screens/planet_abilities_window.py` — accept new
   `on_close_callback: Optional[Callable[[], None]]` kwarg and override
   `kill()` to invoke it before delegating to `super().kill()`. Mirrors
   the pattern in `PlanetListWindow.kill()` (`planet_list_window.py:576-595`).
2. `game/ui/screens/strategy_windows/planet_abilities_ctrl.py` — add a
   `_on_closed` method that resets `composer.planet_abilities_window = None`
   and pass it to `PlanetAbilitiesWindow(..., on_close_callback=self._on_closed)`.
   Mirrors the pattern in `PlanetListRegistrar._on_closed`
   (`list_windows.py:66-67`).

### Follow-Up Suggestions (out of scope for this fix)
- **Cleanup-contract documentation.** PROJ-309 sub-phase 3.10's docstring at
  `strategy_window_manager.py:12-17` flagged the latent bug for the read
  side but did not codify the symmetric write-side rule. Suggest adding
  to `docs/06_UI_STYLE_GUIDE.md` or `docs/03_CONVENTIONS.md`: *whenever a
  slot is added to `has_modal_open`, a corresponding cleanup path
  (registrar `on_close_callback` OR `_handle_window_close` branch) must
  be added in the same change.* The new parametrised guard in
  `test_strategy_window_manager_public_api.py::TestModalSlotCleanupContract`
  enforces this mechanically.
- **Asymmetric `is not None` vs `.alive()` checks.** `has_modal_open()`
  uses `is not None` while `_is_blocking_ui_element_at()` uses
  `window.alive()`. Worth a small follow-up to unify, though now that
  cleanup is enforced on every slot the asymmetry is no longer load-bearing.
