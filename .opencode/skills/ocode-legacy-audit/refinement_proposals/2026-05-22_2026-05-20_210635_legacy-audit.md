## REJECTED items — patterns to address

### Rejection 1: A-04 — TODO without removal target classified as legacy

**Item:** A-04 (Shard 03)
**File:** `game/app.py:459`
**Audit classification:** MINOR — stale TODO without linked PROJ
**Verifier verdict:** REJECTED — wrong-skill

**Why rejected:** `available_tech_ids: list[str] = []  # TODO: Replace with empire.available_tech or similar` is a **feature gap** (the tech tree was never wired up), not a legacy artifact. The TODO marks missing future implementation, not deprecated past implementation. `ocode-legacy-audit` is a removal/consolidation skill; "Replace with X" is forward work, not removal.

**Suggested refinement:** When the deprecation_marker detector encounters a `TODO` (not `# Deprecated:` / `@deprecated` / `warnings.warn(DeprecationWarning, ...)`), check whether the TODO's verb is "Replace with" / "Implement" / "Use X" (forward-looking) vs "Remove" / "Delete" / "Drop" (backward-looking). Forward-looking TODOs are likely wrong-skill (feature gaps belong to product-completion tracking, not legacy audit). Either filter them out of `raw/deprecation_markers.json` or label them with a sub-category like `forward_todo` so the downstream skill can drop them automatically.

### Rejection 2: LEG-A-3 — audit recommended "no action" but still surfaced as actionable

**Item:** LEG-A-3 (Shard 03)
**File:** `game/simulation/services/ship_materializer.py:193-205`
**Audit classification:** MINOR — `set_default_ship_materializer` is test/lab-only
**Audit's own recommendation:** "No remediation needed, but worth noting for potential pattern drift."
**Verifier verdict:** REJECTED — verifier honored audit's own guidance

**Why rejected:** The shard reviewer explicitly wrote "No remediation needed." The downstream skill loaded this into the candidate set because the severity was MINOR (not INFO) and the audit-self-retraction mechanism only filters INFO findings. The result: a finding that the audit itself said skip was still treated as actionable.

**Suggested refinement:** Add a structured `audit_recommendation: skip | act` field to each finding's frontmatter (alongside `severity` and `recommendation`). Findings where the shard reviewer says "no action" / "not a finding" / "leave as-is" should carry `audit_recommendation: skip` so the downstream skill drops them at Phase B without prompting the user. Either that, or downgrade such findings to INFO (which the downstream skill already drops to user-opt-in).

### Rejection 3: LEG-F-2 — Duplicate-system misclassification

**Item:** LEG-F-2 (`legacy_duplicate_systems_cross.md`)
**Files:** `game/ui/screens/workshop_data_loader.py` vs `game/simulation/services/registry_loader.py`
**Audit classification:** MINOR duplicate-system; `reload_registries_from_directory` is the simulation-layer canonical with 0 production callers, so `WorkshopDataLoader` should delegate to it.
**Verifier verdict:** REJECTED — the framing is inverted

**Why rejected:** Verifier confirmed `reload_registries_from_directory` is test-only infrastructure (0 production callers, 37 test callers) and `WorkshopDataLoader.load_all()` is the production canonical (1 production caller). They are NOT duplicates; they serve different architectural needs (test utility vs production UI loader with workshop-specific policy loading and default class detection). The audit identified them as duplicates based on similar low-level operations (clearing registries + loading JSON), but layering analysis shows they are not interchangeable.

**Suggested refinement:** For each candidate duplicate-system pair, the duplicate-system detector should compute a "production-call-site asymmetry" metric: if one implementation has 0 production callers and the other has >0, the test-only side is probably **not** the canonical even if it is in a "simulation layer" location. The audit's existing IS-12 etc. analysis correctly handled this for other pairs (e.g. `ResourceRegistry` vs `ResourceCatalog`); the heuristic just needs to apply to F-2 as well. Add a check: `if call_site_count_production[A] == 0 and call_site_count_production[B] > 0: log_warning("possible test-utility vs production-canonical, not duplicate")` and either downgrade to INFO or include in `findings/verification.md` as a candidate intentional split.

## Verifier-augmented call-site counts (audit undercounted tests)

### LEG-02-012 — load_state caller count

**Item:** LEG-02-012 — `BattleController.load_state`
**Audit said:** "0 production callers (grep-verified)"
**Verifier found:** 0 production callers (audit correct) BUT 4 test callers in `tests/unit/simulation/battle_controller/test_state.py:90, 128, 245, 268`

**Why this matters:** The audit's "Quick Wins" section lists this at Rank 2 as "Delete `BattleController.load_state` — 87 LOC, zero production callers." A reader might interpret "zero callers" as "single-PR pure deletion," but in fact migration of 4 test callers is required first. The audit's text says "zero *production* callers" (correct) but doesn't quantify test callers.

**Suggested refinement:** For every dead-code finding, capture both `call_site_count_production` and `call_site_count_test` as separate numeric fields. The downstream skill's quick-wins surface should only flag items with `call_site_count_production == 0 AND call_site_count_test == 0` as "single-PR deletion." Items with `call_site_count_production == 0 AND call_site_count_test > 0` need a `migrate_test_callers_then_delete` recommendation.

## INFO items the user excluded

**Count:** 0

All 3 INFO-severity findings (LEG-01-005 factory, LEG-01-006 closure, LEG-02-004 ModifierManager) were self-retracted by their shard reviewers as Phase 1 false positives. The downstream skill classified them as OUT_OF_SCOPE at Phase B (they would have been INFO had the reviewers not retracted them) and did not surface them for user opt-in.

**Suggested refinement:** None on INFO classification per se — the self-retraction pattern is working. However, related: the deterministic Phase 1 scanner is producing 6+ wrapper-delegate false positives and 1 name-pair-drift false positive per run, which the Phase 2 reviewers retract. The Phase 1 scanner's wrapper-delegate detector specifically should learn to:
- Distinguish factory methods (Pattern #15) from wrapper delegates by checking if the return type is **different from `self`'s class** AND the wrapped construction is a **constructor call** rather than a method call on another object. `Modifier.create_modifier(value) -> ApplicationModifier { return ApplicationModifier(self, value) }` should not be flagged.
- Distinguish local closures from module-level wrappers by checking whether the function is defined inside another function body. `calc_damage_at_range(r)` inside `_compute_points_of_interest()` should not be flagged.
- Distinguish documented Facade/Delegate (Pattern #5) by checking if the wrapper's class name does NOT match a deprecation-marker pattern AND the wrapped method exists on a documented internal-only class (e.g. `_BY_NAME` dict, `ShipSerializer`). `get_ability_metadata` over `_BY_NAME.get` should not be flagged.

Each of these would reduce the Phase 1 false positive rate noticeably.
