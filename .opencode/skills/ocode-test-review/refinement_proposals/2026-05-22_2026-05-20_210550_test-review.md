## 1. False-Positive Patterns

### FP-1: CAT-5 fixture-scope rescoping ignores fixture mutability

- **Examples (rejected findings):**
  - `S06-F011` — `tests/unit/strategy/conflict_resolution/conftest.py:12-35` — rejected because: MagicMock instances accumulate `call_args_list`/`call_count`/`called`. Session scope would leak state across tests.
  - `S06-F012` — `tests/unit/simulation/armor_mechanics/conftest.py:6-35` — rejected for the same reason; also mutable `hp` / `current_shields` fields persist.
  - `S14-F015` — `tests/unit/simulation/combat/test_damage_calculator.py:331-370` — rejected because factory fixtures **must** be function-scoped for test isolation; class-scope risks shared state across test methods.
- **Adjacent NEEDS_REWORK** (Claude narrowed but didn't reject):
  - `S06-F015` density/conftest.py — `seeded_rng` (stateful PRNG) + `simple_density_map` (mutable DensityMap) must stay function-scoped; only the 6 primitive fixtures may be session-scoped.
  - `S08-F003` test_battle_state_serialization.py — rescope safe but priority is MINOR not MAJOR.
  - `S13-F007` test_race_summary_panel.py — only `mock_race_config_empty` is read-only; others mutate at known lines.
- **Proposed filter:**
  - **Phase 1 deterministic** (preferred when possible): Before raising CAT-5 against a `conftest.py` fixture, scan the fixture body for any of: `MagicMock(`, `Mock(`, `random.Random(`, `numpy.random`, mutable container literal (`{}`, `[]`, `set()`), or any attribute assignment after construction. If found, **either** drop the finding or downgrade severity to MINOR with a `mutability_warning` note.
  - **Phase 2 prompt guidance** (when the check needs human-like judgment): Add to the reviewer prompt: "Before flagging CAT-5 on a fixture, check whether the fixture creates a MagicMock, a stateful PRNG, or any mutable container. MagicMock specifically accumulates `call_args_list`/`call_count` — session/module scope causes cross-test state leak. Default-prefer function scope for any MagicMock fixture."
  - **Verifier guidance**: Phase 3 verifier should recompute mutability check before confirming the finding.

### FP-4: CAT-12 logic-heavy threshold too low

- **Examples (rejected findings):**

- **Proposed filter:**

### NR-1: CAT-2 phantom-method tests sometimes have real production methods with a name variation

- **Examples (needs-rework findings):**
  - `S01-F002` test_workshop_screen.py:300-309 — test patches `_save_ship` (underscore prefix); production method is `save_ship` (no underscore).
  - `S01-F003` test_workshop_screen.py:311-320 — same: `_load_ship` vs `load_ship`.
  - `S01-F004` test_workshop_screen.py:322-331 — same: `_on_select_target_pressed` vs `on_select_target_pressed`.
- **Suggested guidance:** Before suggesting "delete test" for a CAT-2 phantom-method test, grep the production module for the method name **without** the leading underscore (and also strip/swap underscores in case the test author renamed). If a real method exists with a near-matching name, suggest "rewrite to call the real method" rather than "delete" — otherwise the suggestion silently drops coverage of a real flow.

### NR-2: CAT-1 `assert not hasattr` patterns are usually CAT-3 deletion guards

- **Examples (needs-rework findings):**
  - `S12-F002` test_turn_engine_lazy_properties.py:313-320 — `assert not hasattr(turn_engine_module, "create_default_turn_engine")` — CAN fail if symbol is re-added; valid CAT-3 regression guard, not CAT-1.
  - `S07-F003` test_battle_outcome_replay_id.py:23-33 — `hasattr` + None default — original is genuinely CAT-1, but the underlying invariant (`replay_id` propagation) is real and should be replaced with an integration test, not deleted.
- **Suggested guidance:** A test asserting `assert not hasattr(module, "symbol")` is **always** a regression guard — flag as CAT-3 with the "Keep" or "Move to tests/static_guards/" suggestion. A test asserting `hasattr(...)` + default-value-check is borderline CAT-1; the suggestion should be "replace with integration test that exercises the propagation path" not "delete".

### NR-3: Documentation/agent-tooling tests with valid purpose should be moved, not deleted

- **Examples (needs-rework findings):**
  - `S02-F022` test_codex_consult_skills.py — 101 LOC reading `.agents/skills/*.md` and asserting string containment. Valid purpose (agent skill metadata validation), wrong location (`tests/unit/`).
  - `S10-F019` test_codex_interagent_discussion_skills.py — 160 LOC, 10 doc-linting tests, same pattern.
  - `S13-F021` test_codex_project_config.py — 22 LOC validating `.codex/config.toml`.
- **Suggested guidance:** If a test file has zero `game.*` imports and reads only from `.agents/`, `.codex/`, `.opencode/`, or other non-game paths, suggest **"move to `tests/static_guards/` or `tests/tooling/`"** rather than "delete". These tests serve a real purpose but pollute the unit-test directory.

### NR-4: CAT-10 parametrize claims sometimes hide semantic distinctness

- **Examples (needs-rework findings):**
  - `S02-F005` test_pipeline_unification.py — 6 ability tests look identical but each exercises a distinct ability class through a unique production path. Parametrize would obscure semantic coverage boundaries.
  - `S06-F005` test_superweapon_order_pop_matrix.py — 10 weapon tests; Stellerate uses fleet-consumption assertion instead of pop_order assertion; per-weapon Order target structures differ.
- **Suggested guidance:** Before suggesting CAT-10 parametrize, the reviewer should diff the **per-test setup** code, not just the assertion shape. If setup differs by more than parameter values (e.g., different fixture, different mock structure, different assertion target), the cluster is **not** parametrize-eligible. Add to the reviewer prompt: "Parametrize is only appropriate when ≥3 cluster members share identical setup and differ **only** in input/output tuple values."
