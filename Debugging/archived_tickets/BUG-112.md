# BUG-112: Combat Lab visual run results intermittently not recorded in test run history

## Description
When running a visual test in the Combat Lab, the results sometimes fail to appear in the Test Run History panel. Headless runs always record correctly. The behavior is intermittent — in the same session, one visual run recorded successfully while the next did not.

The combat_lab.log confirms the visual run completes and passes (`[TEST LOG] BEAMWEAPON-001 - Mode: UI - Result: PASS`), but no corresponding `add_run` call follows. In contrast, successful recordings show a "Storing visual test results" log entry before `add_run`.

**Root cause analysis:** Visual run results are recorded via `reset_selection()` in `screen.py` after the scene transition back from the battle screen. Unlike headless runs (which call `test_history.add_run()` directly and refresh the results panel), visual runs depend on the scene transition completing and `reset_selection()` being invoked. When this chain breaks, results are lost. Additionally, the results panel lacks an explicit refresh after visual test completion.

## Investigation Report

### Code Path Trace
User clicks "Run Visual" → `screen._on_run()` → `executor.run_visual()` → `screen._switch_to_battle()` → `scene_callback("start_test_battle")` → app switches to BattleScreen → `_run_single_tick()` processes ticks → test completes → `test_completed = True` → user clicks a button to return → app handles return → `start_test_lab()`

### Dependency Map
**Callers of `reset_selection()`:** ONLY `app._handle_battle_action("return_to_test_lab")` at app.py:604
**Callers of `add_run()`:** screen.py:351 (visual via reset_selection), test_executor.py:255 (headless), test_executor.py:376 (batch)

### Root Cause: Two Exit Paths From Battle Screen

There are **two ways** to exit the battle screen back to the test lab:

1. **"Return to Combat Lab" overlay button** (battle_ui.py:105-107) → `trigger_return_to_test_lab()` → `_handle_battle_action("return_to_test_lab")` → **calls `reset_selection()`** → results recorded ✓

2. **ControlPanel "End Battle" button** (battle_panels.py:564-567) → returns `"end_battle"` → `_trigger_return_to_setup()` → `_handle_battle_action("return_to_setup")` → checks `return_state == GameState.TEST_LAB` (app.py:608) → calls `start_test_lab()` **WITHOUT `reset_selection()`** → results lost ✗

In battle_ui.py, the click handling checks the overlay button first (line 102), but if the click misses that rect, it falls through to the ControlPanel (line 114) which has its own "End Battle" / "End Battle Early" buttons. Those route through `return_to_setup`, which does NOT call `reset_selection()`.

### Similar Patterns Found
Headless runs record results synchronously via `test_history.add_run()` directly in `_execute_headless()` (test_executor.py:255). No scene transition dependency.

### Git History Analysis
**Suspect commits:** The BUG-110 fix (uncommitted) added `start_test_battle` handler but did not address the `return_to_setup` path. The `return_to_setup` handler at app.py:606-611 pre-dates the test lab and was originally designed for normal battle setup — it was never updated to handle test mode returning.

### Documentation Discrepancies
None — code matches docs. The scene_callback pattern follows PROJ-65 conventions.

## User Context

**Reproduction Steps:**
1. Open Combat Lab
2. Select a test scenario (e.g., BEAMWEAPON-001)
3. Click "Run Visual"
4. Wait for test to complete in battle screen
5. Click the ControlPanel "End Battle" button (NOT the "Return to Combat Lab" overlay)
6. Observe test run history — no new entry

**Expected Behavior:** Visual run results should appear in test run history regardless of which button the user clicks to exit.
**Actual Behavior:** Results only recorded when using "Return to Combat Lab" button; lost when using "End Battle" button.
**History:** Unclear when this last worked; the dual-button issue has likely existed since the ControlPanel was added.
**Consistency:** Intermittent — depends on which button the user clicks. User reports "not sure" which they use.
**Game State:** Combat Lab → Battle Screen (test mode) → return to Combat Lab.
**Known Workarounds:** Always use the centered "Return to Combat Lab" overlay button.

## Hypothesis Log

### Hypothesis 1: "End Battle" ControlPanel button bypasses reset_selection() - CONFIRMED
**Theory:** When the user clicks the ControlPanel "End Battle" button instead of the "Return to Combat Lab" overlay, the exit path goes through `return_to_setup` which does not call `reset_selection()`.
**Evidence For:**
- Two distinct exit paths exist in the code (return_to_test_lab vs return_to_setup)
- Only return_to_test_lab calls reset_selection()
- return_to_setup routes to test_lab when return_state == TEST_LAB, without reset_selection()
- Session logs show test completion (PASS) without subsequent "Storing visual test results" — consistent with reset_selection never being called
- User reports "Not sure" which button they click — explains intermittency
- Log timeline: First visual run succeeded (5-second gap = clicked overlay), subsequent runs failed (shorter gaps = clicked panel button)
**Evidence Against:** None
**Test:** Fix the return_to_setup path to also call reset_selection() when routing to test lab. Verify results are always recorded.
**Result:** CONFIRMED — code analysis conclusively shows the missing reset_selection() call.
