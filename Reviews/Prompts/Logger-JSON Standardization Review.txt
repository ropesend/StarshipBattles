### Two Sub-Problems

#### Sub-Problem A: Logger Inconsistency (IH-001, IH-020, MOD-CORE-003, ERR-011)

**The problem:** Three competing logging patterns exist across the codebase:

| Pattern | Usage | Files | Example |
|---------|-------|-------|---------|
| **Custom Logger singleton** | `Logger.instance()`, `log_info()`, `log_error()`, `log_warning()` | ~118 files | `from game.core.logger import log_info` |
| **Standard library logging** | `logging.getLogger(__name__)` | ~6 files | `import logging; logger = logging.getLogger(__name__)` |
| **Test lab logger** | `simulation_tests.logging_config.get_logger` | ~4 files | Test infrastructure only |

**Additional logger concerns from prior review:**
- **MOD-CORE-003 (Major):** `Logger.__init__` calls `self.setup()` which creates file handlers during first import — import-time side effects. Creates files on disk during `import`. Problematic in test environments and headless setups.
- **ERR-011 (Minor):** Inconsistent logging levels — some modules overuse `log_error()` for recoverable issues, others underuse for critical failures. No global guidelines on when to use which level.
- **Module-level `_event_handler` global** (MOD-CORE-016) set via `set_event_handler()` but no formal lifecycle management. Persists across test boundaries.

**What agents must deliver:**
1. **Complete inventory** of every file in `game/` and which logging pattern it uses (A, B, or C)
2. **The custom Logger class** — full analysis of `game/core/logger.py`: what it wraps, what it adds beyond standard logging, file handler setup, side effects
3. **Migration impact assessment** — what breaks if we standardize on one pattern? What features does the custom Logger provide that standard logging doesn't?
4. **Recommendation** — which pattern to standardize on, with rationale
5. **File-by-file migration list** grouped by difficulty (simple mechanical replacement vs. needs refactoring)

#### Sub-Problem B: JSON Loading Inconsistency (IH-010, PC-015, ERR-015)

**The problem:** Centralized JSON utilities exist but some files bypass them:

| Pattern | Usage | Count | Example |
|---------|-------|-------|---------|
| **Centralized utility** | `core.json_utils.load_json()` / `save_json()` | ~101 calls in ~30 files | `from game.core.json_utils import load_json` |
| **Direct stdlib** | `json.load(f)` / `json.dump()` | ~18 calls in ~9 files | `import json; data = json.load(f)` |

**Additional JSON concerns from prior review:**
- **PC-015 (Major):** 9 loader/parser classes across `strategy/generation/loaders`, `simulation`, and UI each independently implement open/json.load/error handling — ~100 lines of duplicate file I/O. No `BaseJSONLoader` template.
- **ERR-015 (Info/Positive):** `json_utils.py` exemplifies best practices: specific exceptions, proper logging, exception chaining, clear contracts. This IS the reference implementation.
- **MOD-CORE-015 (Minor):** `json_utils.py` itself catches broad exception categories — `IOError` catches many things beyond "file not found", `TypeError` in save could hide serialization bugs. Could be tightened.

**What agents must deliver:**
1. **Complete inventory** of every `json.load`, `json.dump`, `json.loads`, `json.dumps` call in `game/` — file, line number, context
2. **Every `load_json` / `save_json` call** — file, line number, context
3. **The 9 loader classes** — identify each, document their open/load/error pattern, assess if a BaseJSONLoader template would help
4. **The json_utils.py implementation** — full analysis of what it provides (error handling, path resolution, logging)
5. **Migration plan** — which direct calls should use the utility, which legitimately need direct access (e.g., non-file JSON like string parsing), grouped by difficulty

## Known Concerns from Prior Review

### Logger-Specific:
1. **Import-time side effects** (MOD-CORE-003) — Logger creates file handlers on first import. This is a correctness issue, not just style.
2. **Module-level globals** (MOD-CORE-005, MOD-CORE-016) — `_event_handler` global alongside SingletonMeta. Dual state management.
3. **Test pollution** — Logger singleton state persists. No reliable reset between tests.
4. **Missing level guidelines** (ERR-011) — No documented policy on when to use error/warning/info.
5. **118 files to migrate** if pattern changes — this is a significant effort. The review must assess whether the custom Logger adds genuine value over standard logging, or if it's just a wrapper that adds coupling.

### JSON-Specific:
1. **Only 18 direct calls** — this is a quick win if the review confirms all 18 should migrate.
2. **9 loader classes** (PC-015) — whether to create BaseJSONLoader or just ensure they all use json_utils is a design question.
3. **json_utils error handling** (MOD-CORE-015) — could be tightened (more specific exception types).

### Questions for Agents to Answer:
1. Does the custom Logger provide any functionality beyond standard `logging`? (e.g., file rotation, custom formatting, event system integration)
2. Could we wrap `logging.getLogger(__name__)` to keep custom features while using the standard API?
3. Are any of the 18 direct JSON calls legitimate (non-file JSON, performance-critical paths, test utilities)?
4. Would a BaseJSONLoader help the 9 loaders, or is "just use json_utils" sufficient?
5. What is the correct migration order? (Logger is high-effort; JSON is low-effort)

</areas_of_concern>
