## Focus: Protocol Gap — hasattr/getattr Overuse (600+ occurrences)

The codebase has **606 hasattr/getattr calls across 131 files** but only **~15 Protocol definitions** in `game/core/protocols.py`. This means the vast majority of duck-typing checks are untyped, invisible to IDEs, and fragile during refactoring.

### Prior Review Findings (from 2026-02-23 Deliberate Design Debt Audit)

**PC-003 (Major):** "Protocol Pattern — 590+ hasattr Calls Without Type Safety"
- Location: 606 hasattr/getattr calls across 131 files vs 15 protocols in core/protocols.py
- Only ~15 protocols defined but 606 hasattr/getattr calls suggest 50+ candidates needed
- Impact: Type safety gaps, poor IDE support, refactoring difficulty
- Estimated effort: 2-3 weeks

**DD-017 (Major):** "365 Getattr Calls Suggest Duck Typing"
- Location: 86 files
- Heavy use of `getattr(obj, 'attr', default)` hides missing attributes, poor IDE support
- Assessed as "Could go either way" — some may be backwards compatibility during refactoring, some are protocol-based design
- Recommendation: Add Optional type hints or use proper Protocol definitions

### What This Review Should Produce

1. **Complete inventory** of every `hasattr()` and `getattr()` call site, categorized by:
   - **Category A: Protocol candidates** — checking for an interface (e.g., `hasattr(obj, 'ability_instances')`) → should become a Protocol
   - **Category B: Optional attribute access** — defensive access with defaults (e.g., `getattr(obj, 'name', 'Unknown')`) → should use Optional typing or Protocol
   - **Category C: Dynamic dispatch** — legitimate runtime reflection (e.g., `getattr(self, f'handle_{cmd}')`) → keep as-is, document
   - **Category D: Legacy/transitional** — backwards compat checks from refactoring → should be removed (old system is gone)
   - **Category E: Test code** — test infrastructure using hasattr/getattr → lower priority, may be acceptable

2. **Protocol extraction plan** identifying:
   - Which new Protocols to create (name, attributes, methods)
   - Which existing protocols in `game/core/protocols.py` need expansion
   - Grouping by domain layer (core, simulation, strategy, UI)
   - Migration order (dependencies between protocols)

3. **Per-file migration effort** estimates (Simple/Medium/Complex)

4. **Phased implementation plan** suitable for a PROJ-XX project:
   - Phase 1: Define new Protocols (no call-site changes)
   - Phase 2: Migrate Category A (hasattr → isinstance + Protocol)
   - Phase 3: Migrate Category B (getattr → typed Optional access)
   - Phase 4: Clean up Category D (remove transitional checks)
   - Phase 5: Audit remaining Category C (document as intentional)

### Why This Matters

1. **Refactoring safety:** The codebase is undergoing active god class decomposition (PROJ-86/87/88/89). Moving methods between classes is dangerous when 600+ duck-type checks could silently break.

2. **IDE support:** 606 untyped attribute checks mean IDE "Find Usages", "Rename Symbol", and type checking cannot track these references. Refactoring requires manual grep instead of automated tooling.

3. **New developer onboarding:** Duck typing hides the actual contracts between components. A Protocol definition documents "this is the interface" explicitly.

4. **The project already uses Protocols:** 15 protocols exist in `game/core/protocols.py`, demonstrating the pattern works. This is about completing the migration, not introducing a new pattern.
