## Current State of registry.py (game/core/registry.py)
The file documents three tiers of access in its module docstring:

```
TIER 1 - Domain Services (Computed Access):      # Best: service wraps registry
    ShipStatsCalculator.calculate_ship_stats(design)

TIER 2 - Dependency Injection [RECOMMENDED]:      # Good: explicit provider parameter
    provider = get_default_registry_provider()
    components = provider.get_components()

TIER 3 - Direct Singleton Access:                 # Avoid: hidden global dependency
    RegistryManager.instance().components
```

Key classes/functions:
- `GameRegistries` (frozen dataclass) — holds components, modifiers, vehicle_classes, resources dicts
- `RegistryManager(metaclass=SingletonMeta)` — singleton, has hydrate(), freeze(), clear(), owns all data
- `DefaultRegistryProvider(IRegistryProvider)` — wraps RegistryManager, delegates get_X() calls
- `TestRegistryProvider(IRegistryProvider)` — isolated test data, takes components/modifiers/vehicle_classes (NOT resources)
- `get_default_registries()` → returns module-level `_default_registries` global
- `set_default_registries()` → sets module-level global
- `get_default_registry_provider()` → returns module-level `_default_provider` global
- `freeze_registry()` / `clear_registry()` → lifecycle helpers

## Design Constraints
- **CLAUDE.md policy:** "When a new system replaces an old one, ERADICATE the old system completely." — once DI is chosen, remove all non-DI access
- **Test infrastructure:** 7,353 tests depend on registry access patterns. Migration must not break tests.
- **Composition roots:** `game/app.py` (production) and `tests/conftest.py` (test) are the legitimate places to initialize registries
- **Performance:** Registry lookups are on hot paths (ability aggregation, stat calculation). DI should not add overhead.
