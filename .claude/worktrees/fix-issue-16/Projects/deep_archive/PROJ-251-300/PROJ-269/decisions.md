## Locked architectural decisions (established during planning)

| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-04-12 | Project initialized | Starting point for Unified Battle Simulator Entry/Exit (PROJ-269). |
| 2026-04-12 | **Component damage persists as exact HP per component** on `ShipInstance.components: Dict[str, ComponentState]`. Round-trip through every battle. | User's stated goal is per-component damage that carries across battles. Exact HP (not damage %) avoids rounding drift over many battles and matches the engine's internal representation. |
| 2026-04-12 | **Boundary is a first-class input on `BattleSpec`**, passed into the engine. `None` / `UnboundedRegion` = unbounded combat. Strategy reads default from game settings; Battle Setup exposes to user; Combat Lab scenarios specify per test. | User: "It should be passed in to the combat system, for the strategic layer it can be set in game settings, I'm not sure what a good starting value should be, it should also be possible to have it open ended as a setting." |
| 2026-04-12 | **N teams supported** with explicit per-team `EntryVector`. No alliances — every team is enemy to every other team; no target preference. Ambushes = one team pre-positioned (entry_vector at current location), others entering from hex edges. | User: "Up to N teams with explicit entry vectors." + "Each Team only attacks the enemy players ... with no preference for targets. This will eventually change but I don't think that there will ever be a coordinated team, just teams that don't shoot at each other." Coordinated-allied-team is future work; no-shoot-at-each-other is a future "non-aggression" layer, not part of this project. |
| 2026-04-12 | **Modifiers live in a single `ModifierStack` on `BattleSpec`**, applied by the engine at init. Each context's compiler walks its own data (species, empire, system, sector) and emits the stack. Ships are NOT pre-mutated with modifier effects. Existing two-phase aggregation (intra-group MAX, inter-group SUM) is reused; each entry carries a `source` string for traceability. | User: "A single ModifierStack on the BattleSpec — applied by mode handler at battle start (Recommended)". Ensures ships enter the engine unmutated (no layer violations), modifier provenance is traceable, and Combat Lab can test a stack explicitly without reconstructing ships. |
| 2026-04-12 | **Formations authored per TaskForce** with design_role-based defaults. `TaskForce.formation: Optional[FormationSpec]`. `FormationResolver` converts (formation, entry_vector, boundary, ships) → per-ship (position, angle) at battle start. UI for player authoring is a separate future project; the model, resolver, and defaults land in PROJ-269. | User: "Formation per TaskForce, authored by player, defaults chosen by design_role (Recommended)". Per-TaskForce granularity lets mixed fleets (carriers + escorts) position correctly; coarser per-fleet would prevent that. |
| 2026-04-12 | **Retreat = boundary exit with 'retreat' policy.** Not a separate engine mechanic. A ship crossing the boundary with `ExitPolicy.RETREAT` is removed from the battle and marked `ShipStatus.RETREATED` in the outcome. Unbounded battles cannot have retreat. | User: "Retreat = boundary exit with 'retreat' policy (Recommended)". Single mechanic for both "ship warps out" and "ship flees arena" — no dual bookkeeping. |
| 2026-04-12 | **Three telemetry levels: MINIMAL / NORMAL / DETAILED.** Implemented as opt-in `CombatEventBus` subscribers. MINIMAL attaches nothing; NORMAL attaches weapon summaries + ship stats; DETAILED additionally attaches a full hit-log recorder. Strategy defaults NORMAL, Battle Setup NORMAL, Combat Lab DETAILED. | User: "Three levels: MINIMAL / NORMAL / DETAILED (Recommended)". Per-context defaults match usage patterns (batch testing wants speed; Combat Lab wants forensic detail). |
| 2026-04-12 | **Migration is phased, least risk first.** Six phases; each independently shippable; game remains runnable at every commit; old and new paths coexist until Phase 6 deletes the legacy code. | User: "Phased, in order of least risk (Recommended)". Avoids a long broken-trunk window; allows bisecting regressions; each phase has focused test coverage. |
| 2026-04-12 | **Design the component HP model now, defer the repair mechanic.** Phase 2 adds `ShipInstance.components` and round-trip persistence. Ships accumulate damage across battles. Repair (shipyard / over-time / repair-components-on-fleet) is a separate future project. | User: "Design the component HP model now, defer repair mechanic (Recommended)". Unblocks this project; accumulating damage across battles is actually a desirable realism property during playtest. |
| 2026-04-12 | **Replace `BattleMode` enum and `BattleModeHandler` hierarchy with explicit fields on `BattleSpec`.** Variance moves from a switch (mode=TEST → clone? retreat? headless?) to named fields (`boundary`, `end_condition`, `modifier_stack`, `telemetry_level`, `post_battle_hook`). The engine reads these fields directly; no handler lookup. | User: "Replace with explicit fields on BattleSpec (Recommended)". Removes hidden behaviour; two battles are comparable by diffing their specs; callers set exactly what they need. |
| 2026-04-12 | **Compiler per context.** Each caller (strategy / battle setup / combat lab) owns a `build_*_battle_spec()` function that translates its domain inputs into a `BattleSpec`. Engine entry is one call: `run_battle(spec) -> BattleOutcome`. | Keeps domain knowledge in the domain layer; engine stays context-blind; testable in isolation. |
| 2026-04-12 | **`BattleSpec` + `BattleOutcome` live in `game/simulation/`.** Every layer can import them; simulation does not import strategy/UI. | Preserves layer boundaries documented in `docs/01_ARCHITECTURE.md`. |
| 2026-04-12 | **Formation defaults by dominant design_role in TaskForce.** Strike → WEDGE; Carrier → CARRIER_PROTECTED; Defender → LINE_ABREAST; Scout/Skirmisher → LINE_ASTERN; mixed → LINE_ABREAST. | Sensible defaults for each doctrine; `None` formation on a TaskForce resolves via this table. Player override is a UI-layer concern. |
| 2026-04-12 | **Post-battle effects via `PostBattleHook` closure on `BattleSpec`.** Strategy attaches a hook that writes `ShipOutcome.components` back to `ShipInstance.components`, removes dead ships from fleets, and applies empire-level effects. Battle Setup and Combat Lab do not attach a hook (Battle Setup shows UI; Combat Lab runs validation on the outcome). | Generalizes the current `FleetBattleAdapter.update_from_battle_results` pattern into a first-class field; removes the layer violation where the strategy adapter reached into simulation results via side effects. |

## Future decisions
(Record new decisions below as they are made during implementation.)

| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-04-12 | **Phase 1 transitional `ship_builder` kwarg on `run_battle`.** Added `ship_builder: Callable[[ShipSpec], Ship]` required kwarg because ShipSpec (pure DTO) cannot carry pre-built Ship instances, and Phase 1 has no universal `Ship.from_spec(spec, registries)` factory. Each compiler supplies its own builder closure. Phase 2 keeps this pattern but `run_battle` now applies `ShipSpec.components` per-instance HP onto the ship after the builder returns — so the builder still only needs to know how to materialize a Ship from design_id. `ship_builder` will be removed or folded into the engine in a later phase once `Ship.from_spec` subsumes it. | Layer rule: DTO in simulation; ship construction varies per context (Combat Lab has JSON files; strategy has ShipInstance; Battle Setup pre-builds). Builder closure keeps each context's expertise local to its compiler. |
| 2026-04-12 | **Phase 1 extra kwarg `pre_tick_loop_callback` on `run_battle`.** One-shot hook fired after `engine.start()` and before the first tick. Used by Combat Lab runner to invoke `scenario.custom_setup(engine)` without introducing a dedicated setup-phase. | The scenario's `custom_setup` expects to run after engine state is initialized but before any ticks happen. Without this hook, custom_setup would have to run mid-tick-loop (too late). Clean alternative; doesn't bloat the DTO. |
| 2026-04-12 | **Phase 2 `CombatPolicies` / `AIPolicy` / `ComponentState` file locations.** Manifest originally listed `game/strategy/fleets/component_state.py`, but the existing codebase places `ShipInstance` et al. at `game/strategy/data/`. `ComponentState` lives at `game/strategy/data/component_state.py` to match neighbors. `CombatPolicies` / `AIPolicy` are new DTOs in `game/simulation/battle_spec.py` (cannot import from strategy). | Mirrors where existing siblings live; avoids creating a new `fleets/` subdirectory. Strategy can't be imported by simulation. |
| 2026-04-12 | **Phase 2 `components` coexists with legacy `component_damage`.** `ShipInstance.components: Dict[str, ComponentState]` is the new authoritative source for the PROJ-269 battle round-trip (instance-index aware). The pre-existing `component_damage: Dict[str, int]` (single-instance granularity, read by 43 files including stat calculators) is kept and mirrored by the Phase 2 update path. Full consolidation is a post-PROJ-269 cleanup. | Replacing `component_damage` in place would be a 40+ file refactor outside PROJ-269's scope. Additive approach is less risky and lets PROJ-269 ship. |
| 2026-04-12 | **Phase 2 retreated ships = remove from fleet (MVP).** When a `ShipOutcome.status == RETREATED`, `apply_outcome_to_fleets` simply removes the ShipInstance from its parent `Fleet.ships` list. The "ship disperses to a scattered remnant fleet at an adjacent hex" logic is deferred to a later project. Mark-as-retreated status on ShipInstance was considered but rejected — the flag would rot as call sites evolve. | User-facing behavior for retreated ships is currently undefined; removal is the simplest mechanic that lets tests pass and the game keep running. Scattered-remnant handling can be bolted on later without rewriting the hook. |
| 2026-04-12 | **Phase 5 telemetry overhead baseline (2026-04-12 run):** MINIMAL ~30ms, NORMAL ~28ms, DETAILED ~28ms for a 500-tick 1v1 reference battle (ships at 1000px apart, minimal combat events fire). All three levels essentially equal when events are sparse. Smoke test thresholds: MINIMAL must not exceed NORMAL by >30%; DETAILED must not exceed MINIMAL by >5x. | Tight event traffic in this smoke scenario means subscriber overhead is negligible. Realistic battles with frequent hits will show more divergence; re-measure when the end-to-end pipeline fires more events. The smoke test in `tests/performance/test_telemetry_overhead.py` is a regression gate, not a precision benchmark. |
| 2026-04-12 | **Phase 5 `HitRecord.modifiers_applied` stays empty in MVP.** Populating the per-hit modifier trace requires wiring `ModifierStack` provenance through `DamageCalculator` and attaching modifier source strings on each `CombatEvent`. That's a larger refactor than the Task 5.3 budget and is not exercised by any current caller. The DTO field exists (Phase 1); population is deferred. | Scope containment. Forensic modifier UI consumers don't exist yet, so an empty tuple is harmless. When a UI or test needs it, wire it through then. |
| 2026-04-12 | **Phase 5.5 inserted between Phase 5 and Phase 6** — closes the `ModifierStack` application gap identified at Phase 5 wrap. `run_battle` now threads `spec.modifier_stack` onto the engine; `FleetAuraManager.initialize(..., modifier_stack=...)` translates entries into its existing `ExternalModifier` pipeline; `HitLogRecorder` captures the active stack on each hit. This unblocks Phase 6's deletion of `SimulationBattleResolver.__apply_shield_interference` / `__apply_strategic_modifiers` ship-mutation side channels. | Without this bridge, Phase 6 would either leave ship-mutation side channels in place (violating PROJ-269's goal) or delete them and break existing behavior. Phase 5.5 completes the plumbing so deletion is safe. |
| 2026-04-12 | **Phase 5.5 placeholder effects are silently skipped by the engine.** Compilers (Battle Setup, strategy) currently emit `ModifierEffect(stat_key="placeholder", value=0)` for toggles whose real effect mapping isn't authored yet. `FleetAuraManager._append_external_from_entry` and `HitLogRecorder._trace_modifiers_for_team` both filter them out. | Compilers record "a toggle was active" even when they don't know the effect — useful for forensic trace later, harmless for battle math today. When content work maps toggles to real `stat_key` values, no engine change needed. |
| 2026-04-12 | **Phase 5.5 `HitRecord.modifiers_applied` = active-at-hit-time set, NOT per-hit contribution set.** The recorder captures "these modifiers were in effect when this hit happened" (globals + attacker team entries, placeholders filtered) rather than "these modifiers specifically contributed to this damage value". True contribution tracing needs thread-through-damage-pipeline plumbing that's out of PROJ-269 scope. | The MVP is useful: a forensic UI can display "shield_booster was active on this hit" without needing to decompose damage math. Upgrading to per-hit contribution is a targeted follow-up when a consumer requires it. |
