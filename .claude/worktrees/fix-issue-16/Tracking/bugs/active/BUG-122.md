# BUG-122: Multiple fleets disappear when joining each other in the same hex — mutual-join + redirect-without-self-exclusion

## Description

During QA Session 20260428_052952 [06:06], the user had 5 fleets (one
ship each) and gave 4 of them JOIN orders targeting the other fleets.
After all the fleets converged, **every fleet and every ship was gone**.
No event log entries explained the disappearances; the player has no
recovery path.

The user initially hypothesised mutual-join (A→B and B→A) as the cause;
log evidence below confirms that exactly that happened in this run, and
a code review uncovered an additional structural failure that compounds
the problem (`redirect_pursuers` doesn't exclude the absorbing fleet,
so it can plant self-targeting orders mid-iteration).

From [BUG-122_logs/battle.log](BUG-122_logs/battle.log) at 06:05:19,642

    2026-04-28 06:04:21,922 - OrderProcessor [Instant]: Fleet 4 merging into 5
    2026-04-28 06:05:19,642 - OrderProcessor [Instant]: Fleet 2 merging into 3
    2026-04-28 06:05:19,642 - OrderProcessor [Instant]: Fleet 3 merging into 2
    2026-04-28 06:05:19,642 - OrderProcessor [Instant]: Fleet 6 merging into 2
    2026-04-28 06:05:19,963 - OrderProcessor [Instant]: Fleet 5 merging into 2

Lines 80275–80277 of `battle.log` show three merges scheduled in the
same `process_instant_orders` call:
- Fleet 2 → Fleet 3
- Fleet 3 → Fleet 2  ← **mutual join with the line above**
- Fleet 6 → Fleet 2

Then on a later tick (line 81255), Fleet 5 attempts to merge into
Fleet 2 — but by then Fleet 2 has already been removed by the mutual
merge above. Fleet 5's ships transfer to a dead reference and Fleet 5
is removed.

Net result: Fleets 2, 3, 5, 6 all destroyed; their ships orphaned in
dead Python references.

## Root Cause Analysis

### Failure 1: Snapshot-then-iterate without re-validation

[game/strategy/engine/order_processor.py:762-779](../../../game/strategy/engine/order_processor.py#L762-L779)
builds `fleets_to_merge` as a one-shot snapshot, then iterates and
merges sequentially. No guard re-checks whether the source or target
fleet is still alive when each tuple's turn comes. References captured
at collection time stay valid Python references even after their fleet
has been removed from `empire.fleets`.

### Failure 2: `_execute_fleet_merge` removes the source unconditionally

[`order_processor.py:97-98`](../../../game/strategy/engine/order_processor.py#L97-L98):
```python
fleet.merge_with(target_fleet, event_bus=self._event_bus)
empire.remove_fleet(fleet, event_bus=self._event_bus)
```
The `remove_fleet` runs regardless of whether `merge_with` actually
transferred ships into a live target. If the target was just absorbed
by a prior iteration, the source's ships transfer to a now-orphaned
Python object and the source is still removed — silent ship loss.
No `FLEET_JOINED` or `FLEET_JOIN_CANCELLED` event covers this state.

### Failure 3: `redirect_pursuers` doesn't exclude `other_fleet` (self-join order creation)

[`fleet.py:363`](../../../game/strategy/data/fleet.py#L363):
```python
redirected = self._pursuer_tracker.redirect_pursuers(other_fleet)
```

When F1 absorbs into F2, this redirects every pursuer of F1 to target
F2. **`other_fleet` (F2) itself is not excluded.** If F2 had a join
order pointing at F1, F2 was registered as a pursuer of F1; after the
redirect, F2's order rewrites to target F2 — a **self-join order**.

`Fleet.merge_with(self)` is then catastrophic ([fleet.py:391-392](../../../game/strategy/data/fleet.py#L391-L392)):
```python
other_fleet.ships.extend(self.ships)   # F2.ships.extend(F2.ships) — DOUBLES the list
self.ships.clear()                      # then empties it — net 0 ships
```
The fleet ends with an empty ship list, then `empire.remove_fleet`
strips the fleet from the empire. Silent total ship loss for that
fleet.

In the user's logged scenario the snapshot was already built before
the redirect fired, so `_execute_fleet_merge(F3, F2, ...)` used the
snapshot's stale F2 reference rather than F3's now-self-targeted
order. But the redirect-without-self-exclusion bug remains a separate
failure mode that can fire any time a join target absorbs its own
pursuer.

## Failure Modes Confirmed or Plausible

1. **Mutual join (A↔B):** snapshot includes both directions; first
   merge runs, source removed; second merge runs against the dead
   target, source's ships orphaned, source removed. **Confirmed in
   the QA logs above.**
2. **Self-join via redirect:** absorbing fleet was a pursuer of the
   absorbed fleet → redirect creates a self-targeting order →
   `merge_with(self)` doubles-then-clears the ship list.
3. **Cycle of 3+:** F1→F2, F2→F3, F3→F1. Snapshot iteration consumes
   the cycle from the front, leaving F3's tuple to run against a
   long-dead F1 reference. F3 vanishes silently.
4. **Convergent join with mid-list target absorbed:** if target X is
   itself a source elsewhere in the snapshot and gets removed before
   pursuers of X are processed, all pursuers of X transfer ships into
   the dead X and are removed.

## Reproducer

Add to `tests/integration/strategy/test_fleet_join_redirect.py`:

```python
def test_mutual_join_both_fleets_disappear():
    """REGRESSION: Fleet A↔B mutual join at same location consumes both."""
    empire, f = make_empire_with_fleets("a", "b")
    f["a"].location = HexCoord(50, 0)
    f["b"].location = HexCoord(50, 0)
    f["a"].add_order(Order(OrderType.JOIN_FLEET, target=f["b"]))
    f["b"].add_order(Order(OrderType.JOIN_FLEET, target=f["a"]))

    OrderProcessor().process_instant_orders([empire])

    # Expect at least one survivor; current code leaves empire.fleets empty.
    assert len(empire.fleets) >= 1, "Both fleets vanished in mutual join"


def test_redirect_does_not_create_self_join_order():
    """REGRESSION: redirect_pursuers must not point a fleet at itself."""
    empire, f = make_empire_with_fleets("a", "b")
    f["a"].location = HexCoord(50, 0)
    f["b"].location = HexCoord(50, 0)
    # B targets A. When A is absorbed into B, B's order must not become
    # 'join B' (self).
    f["b"].add_order(Order(OrderType.JOIN_FLEET, target=f["a"]))

    f["a"].merge_with(f["b"])

    b_order = f["b"].get_current_order()
    if b_order and b_order.type == OrderType.JOIN_FLEET:
        assert b_order.target is not f["b"], (
            "redirect created a self-join order"
        )


def test_three_fleet_cycle_does_not_consume_all():
    """REGRESSION: F1→F2, F2→F3, F3→F1 cycle must not eat every fleet."""
    empire, f = make_empire_with_fleets("a", "b", "c")
    for fleet in f.values():
        fleet.location = HexCoord(50, 0)
    f["a"].add_order(Order(OrderType.JOIN_FLEET, target=f["b"]))
    f["b"].add_order(Order(OrderType.JOIN_FLEET, target=f["c"]))
    f["c"].add_order(Order(OrderType.JOIN_FLEET, target=f["a"]))

    OrderProcessor().process_instant_orders([empire])

    assert len(empire.fleets) >= 1, "Cycle of 3 consumed every fleet"
```

## Suggested Fix Path (not prescriptive)

1. **Pre-merge validation in the iteration loop** at
   [`order_processor.py:775`](../../../game/strategy/engine/order_processor.py#L775):
   skip the merge if either source or target is no longer in
   `empire.fleets`. Emit `FLEET_JOIN_CANCELLED` when the target is
   gone so the player sees an audit trail.
2. **Exclude `other_fleet` from `redirect_pursuers`** at
   [`fleet.py:363`](../../../game/strategy/data/fleet.py#L363).
   `redirect_pursuers(other_fleet)` should not redirect `other_fleet`
   to itself; if `other_fleet` is in its own pursuer list (it had a
   join order against the fleet being absorbed), drop the order
   entirely with a `FLEET_JOIN_CANCELLED` event rather than rewriting
   the target.
3. **Mutual-join collapse** (cleanest): detect mutual pairs in
   `fleets_to_merge` before iteration and replace both entries with a
   single canonical merge (smaller-id-into-larger-id, say). Same for
   cycles — detect the cycle and elect a single survivor with a
   single combined merge.
4. **Always check `len(other_fleet.ships)` before `empire.remove_fleet(self)`**
   in `_execute_fleet_merge` — if the target is dead and ships didn't
   actually transfer, log a warning + emit `FLEET_JOIN_CANCELLED` and
   leave the source alone (or pop the order so the player can re-issue).

## Priority

**Critical** — silent destruction of player ships, no recovery, no
audit trail in the event log. Affects core fleet-management gameplay.

## Status

**Awaiting User Verification** (2026-04-28). Three coordinated fixes
landed:

1. `redirect_pursuers` gains keyword-only `exclude` set; returns
   `(redirected, excluded)` tuple. Excluded pursuers are not rewritten
   and not transferred to `new_target`.
2. `Fleet.merge_with` passes `exclude=frozenset({other_fleet})`. For
   each excluded pursuer, drops stale `MOVE_TO_FLEET`/`JOIN_FLEET`
   orders targeting `self` and emits `FLEET_JOIN_CANCELLED` with
   `reason="self_target_after_redirect"`. New helper
   `Fleet.remove_orders_by_type_and_target`.
3. `OrderProcessor.process_instant_orders` rewritten as Phase A
   (collect) → Phase B (`_elect_canonical_merges` collapses mutual
   pairs, most-ships-wins, smaller-id tiebreaker) → Phase C (execute
   with per-iteration aliveness re-validation; skips emit
   `FLEET_JOIN_CANCELLED` with `reason="absorbed_by_other_merge"` or
   `"target_absorbed_mid_iteration"`).

Test coverage: 5 new integration tests in
`tests/integration/strategy/test_fleet_join_redirect.py` (mutual equal
ships, mutual unequal ships, redirect-no-self-join,
3-fleet-cycle-no-loss, convergent-target-absorbed-mid-iteration) +
3 unit tests in `tests/unit/strategy/fleet/test_fleet_pursuer_tracker.py`
covering the `exclude=` kwarg contract. All 16036 sharded tests pass.

Docs updated: `docs/systems/orders_system.md` JOIN_FLEET edge cases
subsection + reason taxonomy table. `docs/systems/strategy_layer.md`
`redirect_pursuers` signature note.
