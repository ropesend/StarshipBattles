# BUG-116: Workshop quick-add places armor components in wrong layer (CORE/OUTER instead of ARMOR)

## Description
When using the '+' quick-add button in the ship designer / workshop component
palette, armor-classified components (Armor Plate, Emissive Armor, Scattering
Armor, etc.) are placed into the CORE or OUTER layer instead of the dedicated
ARMOR layer.

Reproduced in QA Session 20260427_151244 at 15:13. Screenshot shows Armor Plate
x3 in CORE, Emissive Armor x4 in OUTER, and the ARMOR layer empty (0/300t):

[![Armor placed in CORE and OUTER instead of ARMOR layer](../../../tools/qa_observer/session_data/20260427_151244/images/bug_capture_151345.png)](../../../tools/qa_observer/session_data/20260427_151244/images/bug_capture_151345.png)

## Expected Behaviour
Armor components must be **restricted** to the ARMOR layer. They must not be
permitted in CORE, INNER, or OUTER under any circumstances — neither via
quick-add nor via manual placement.

## Code Investigation
- Layer placement resolved by `WorkshopLayerOps.resolve_target_layer()` in
  `game/ui/screens/workshop_viewmodel_layer_ops.py:53-103`.
- Algorithm: find all layers that pass `LayerRestrictionDefinitionRule._do_validate`
  in `game/simulation/validation/ship_validator.py:137-167`, then return the
  **innermost** layer by `LayerType` value (CORE=1, INNER=2, OUTER=3, ARMOR=4).
- ARMOR layer has `"allow_classification:Armor"` in `data/vehiclelayers.json`,
  but CORE/INNER/OUTER do **not** carry a matching `"block_classification:Armor"`.
  Armor components therefore pass validation in all four layers; innermost wins,
  so they land in CORE/OUTER and the ARMOR layer is left empty.

## Suggested Fix
Add `"block_classification:Armor"` to the CORE, INNER, and OUTER layer definitions
in `data/vehiclelayers.json` for every vehicle template. This:
1. Forces quick-add to choose the ARMOR layer (only valid option).
2. Prevents manual placement of armor in non-armor layers via the existing
   `LayerRestrictionDefinitionRule` validation path.
3. Keeps the design intent purely data-driven — no special-case logic in
   `resolve_target_layer`.

Verify all five layer configurations in `vehiclelayers.json` carry the block rule.
Existing ship designs containing armor components in non-armor layers must be
flagged by validation; loading such designs should fail or auto-migrate (decide
during fix).

  meet the expected behaviour ("not permitted... neither via quick-add nor via
  manual placement"):

  ### Part 1 — Data fix (closes quick-add and design-load paths)

  Added `"block_classification:Armor"` to every non-ARMOR layer entry across
  all five vehicle templates in `data/vehiclelayers.json` (11 layer entries
  total: Capital_Standard CORE/INNER/OUTER, Capital_Escort CORE/OUTER,
  Fighter_Standard CORE, Satellite_Standard CORE/OUTER, Planetary_Complex
  CORE/INNER/OUTER). The ARMOR layer's existing
  `"allow_classification:Armor"` whitelist is preserved.

  This closes:
  - Workshop quick-add (`'+'` button) — `WorkshopLayerOps.resolve_target_layer`
    no longer finds CORE/INNER/OUTER as valid candidates for armor; ARMOR
    becomes the only valid layer.
  - Initial design load (`ShipSerializer._load_components`) — same
    `validate_addition` path.

  ### Part 2 — Production-code fix (closes manual-move path)

  `VehicleDesignService.move_component`
  (`game/simulation/services/vehicle_design_service.py:301`) previously
  bypassed every addition rule on the re-add step. The comment claimed
  "mass budget is advisory" but the implementation skipped the entire
  `addition_rules` list, including `LayerRestrictionDefinitionRule`. So
  manual drag/drop or move-up/move-down arrows on the workshop UI silently
  succeeded even with the data fix in place.

  Replaced the blanket bypass with iteration of `validator.addition_rules`
  that skips ONLY `MassBudgetRule` (preserving the original "budgets are
  advisory for moves" intent). Validation failure now rolls back the
  source-layer removal so the move is fully atomic. Also added the
  pre-existing missing `ship.recalculate_stats()` after a successful
  move (side-benefit cleanup).
