# BUG-106: "Select Move Type" dialog click passes through to hex map, creating duplicate move orders

## Description
When a fleet's move target has another fleet present, a "Select Move Type" dialog appears with "Move to Sector (Static)" and "Intercept Fleet (Dynamic)" buttons. Clicking either button also registers as a hex map click, adding a second unintended MOVE order.

The root cause is that `prompt_move_choice()` in `strategy_window_manager.py` creates a `UIWindow` that is never stored in a tracked attribute. The click-blocking system in `strategy_event_router.py:_is_blocking_ui_element_at()` only checks a hardcoded list of known window attributes, so the dialog is invisible to click blocking. The `MOUSEBUTTONDOWN` event fires both the button callback and the map click handler.

### Key Code Locations
- `game/ui/screens/strategy_window_manager.py` — `prompt_move_choice()` creates untracked `UIWindow`
- `game/ui/screens/strategy_event_router.py` — `_is_blocking_ui_element_at()` hardcoded window list missing the move choice dialog
- `game/ui/screens/strategy_event_router.py` — `has_modal_open()` also doesn't track the dialog
- `game/ui/screens/strategy_click_dispatcher.py` — `_handle_move_mode_click()` calls `prompt_move_choice()` and defines callbacks
- `game/ui/screens/strategy_input_handler.py` — `handle_event()` routes both UI events and mouse clicks in the same pass

### Event Flow
1. User clicks button on dialog → pygame_gui generates `UI_BUTTON_PRESSED`
2. `strategy_event_router.route_event()` processes button, fires callback (adds move order, kills dialog)
3. Same `MOUSEBUTTONDOWN` event continues to `handle_click()`
4. `_is_blocking_ui_element_at()` doesn't know about the dialog → click reaches hex map
5. Second MOVE order created for the hex behind the button

## Investigation Report

### Code Path Trace
```
User clicks dialog button → MOUSEBUTTONDOWN event
  → StrategyScreen.handle_event()
    → StrategyInputHandler.handle_event()           [strategy_input_handler.py:40]
      → ui.handle_event(event)                       [line 61]
        → UIManager.process_events(event)            [detects button hit]
        → WindowManager.process_ui_callbacks(event)  [strategy_window_manager.py:550]
          → Fires on_move()/on_intercept() callback
          → win.kill()  ← dialog destroyed
      → MOUSEBUTTONDOWN still active                 [line 72-74]
        → handle_click(mx, my, button)
          → _is_blocking_ui_element_at()             [strategy_event_router.py:277]
            → Returns FALSE (dialog not in tracking list)
          → dispatch_click()                         [strategy_click_dispatcher.py]
            → Creates SECOND move order at hex behind button
```

### Dependency Map
**Callers of `prompt_move_choice()`:**
- `ClickModeDispatcher._handle_move_mode_click()` (strategy_click_dispatcher.py:113)
- `ClickModeDispatcher._handle_select_mode_click()` (strategy_click_dispatcher.py:363)

**`_is_blocking_ui_element_at()` hardcoded list (strategy_event_router.py:296-306):**
- fleet_orders_window, planet_list_window, fleet_report_window, transfer_dialog
- build_queue_list_window, empire_build_queue_window, event_log_window
- empire_panel_window, _pending_confirmation_dialog
- **MISSING: move choice dialog** (not stored as attribute)

### Similar Patterns Found
All other modal windows follow a consistent pattern:
1. Custom class extending UIWindow (e.g., PlanetSelectionWindow, FleetSelectionWindow)
2. Stored as instance attribute on StrategyWindowManager (e.g., `self.fleet_orders_window`)
3. Added to `_is_blocking_ui_element_at()` hardcoded list
4. Added to `has_modal_open()` check

The move choice dialog violates ALL of these — it creates a raw UIWindow as a local variable `win` (strategy_window_manager.py:521), never stores it, and uses `self.ui_callbacks` for button handling.

## User Context

**Reproduction Steps:**
1. Start a strategy game with multiple fleets
2. Select a fleet and issue a MOVE order
3. Click on a hex that contains another fleet
4. The "Select Move Type" dialog appears
5. Click either "Move to Sector (Static)" or "Intercept Fleet (Dynamic)"

**Expected Behavior:** One move order is created matching the button choice.
**Actual Behavior:** Two move orders are created — one from the button callback, one from the click-through to the hex map.

**History:** Never worked correctly — feature was never integrated with click-blocking system.
**Consistency:** Fails every time.
**Game State:** Strategy map, fleet selected, MOVE mode active.
**Known Workarounds:** None discovered.

**Scope Decision:** User wants all untracked dialogs fixed (CargoQuickDialog, PlanetSelectionWindow, SystemSelectionWindow, FleetSelectionWindow), not just the move choice dialog. No click-through issues observed with other dialogs yet, but they share the same architectural gap.

## Hypothesis Log

### Hypothesis 1: Untracked window invisible to click-blocking — CONFIRMED
**Theory:** `prompt_move_choice()` creates a UIWindow as a local variable that is never stored as an instance attribute on StrategyWindowManager. The `_is_blocking_ui_element_at()` method only checks a hardcoded list of known attributes, so the dialog is invisible to click blocking. The same MOUSEBUTTONDOWN event fires both the button callback (via `process_ui_callbacks`) and the map click handler (via `handle_click`).
**Evidence For:**
- `win` is a local variable at strategy_window_manager.py:521 — never assigned to `self.*`
- `_is_blocking_ui_element_at()` at strategy_event_router.py:296-306 has no entry for the move choice dialog
- `handle_event()` at strategy_input_handler.py:61-74 processes both `ui.handle_event(event)` and then `handle_click()` for the same MOUSEBUTTONDOWN
- Bug reproduces 100% of the time
- All other tracked windows (fleet_orders, transfer_dialog, etc.) DO block clicks correctly
**Evidence Against:** None.
**Test:** Click the dialog button and check if two MOVE orders are created. Verify dialog window is not in any tracking attribute.
**Result:** CONFIRMED — root cause is the untracked window + hardcoded blocking list.
