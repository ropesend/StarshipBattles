### Target Duplication Clusters (7 Primary + 4 Secondary)

These were identified by the Duplication Analyst (DUP), Pattern Cataloguer (PC), and Inconsistency Hunter (IH) agents. Agents should verify these findings, map ALL call sites, and design concrete APIs.

#### Cluster 1: UI Font/Color Initialization Boilerplate (DUP-001)
**Severity:** Critical
**Occurrences:** 10+ files
**Locations:** test_lab/, builder/, battle_state_viewer.py, modifier_impact_grid.py
**Problem:** Every UI component manually initializes identical font sizes, colors, background/border colors. Each screen re-declares the same pygame.font.Font objects and color tuples.
**Missing Abstraction:** `UITheme` or `PanelStylesheet` class
**Estimated duplicate lines:** 200+

#### Cluster 2: Pygame Drawing Boilerplate (DUP-002)
**Severity:** Critical
**Occurrences:** 810+ pygame.Rect() calls, 300+ blit calls, 247+ pygame.draw calls across 86+ files
**Hotspot:** test_lab/ (79+ blit calls in test_run_details.py alone)
**Problem:** Repetitive drawing code for rectangles, borders, text rendering. Common patterns: draw rounded panel, draw titled section, draw text with color, draw progress bar.
**Missing Abstraction:** `DrawingUtils` or `PanelDrawer` helper class
**Estimated duplicate lines:** 400+

#### Cluster 3: Ability Value Extraction (DUP-003 + DUP-012)
**Severity:** Major
**Occurrences:** 14 instances of value extraction + 28 isinstance(data, dict) checks across 10 ability files
**Locations:** defense.py (5), crew.py (3), propulsion.py (6), weapons.py, sensors.py
**Problem:** Every ability repeats: `val = data if isinstance(data, (int, float)) else data.get('value', 0)` and/or `if isinstance(data, dict): ... else: ...`
**Missing Abstraction:** `_extract_value()` helper on Ability base class
**Estimated duplicate lines:** 80+

#### Cluster 4: Ability recalculate() and get_ui_rows() Boilerplate (DUP-004)
**Severity:** Major
**Occurrences:** 19 recalculate() methods, 21 get_ui_rows() methods across 7 ability files
**Problem:** Nearly identical recalculate() pattern (base * mult) and get_ui_rows() format string pattern repeated in every ability class
**Missing Abstraction:** `SimpleMultiplierAbility` base class with class-level configuration
**Estimated duplicate lines:** 150+
**Risk:** HIGH — this touches core simulation, needs extremely careful test coverage

#### Cluster 5: ValidationResult Factory Methods (DUP-005)
**Severity:** Major
**Occurrences:** 42 instances across 6 files
**Locations:** command_handlers.py (16), superweapon_command_handlers.py (14), validators (12)
**Problem:** Repeated `ValidationResult(is_valid=False, errors=[...])` and `ValidationResult(is_valid=True)` patterns
**Missing Abstraction:** Factory methods: `ValidationResult.error("msg")`, `ValidationResult.success()`, `ValidationResult.errors(["msg1", "msg2"])`
**Estimated duplicate lines:** 100+
**Risk:** LOW — additive change, no behavior modification

#### Cluster 6: Command Handler Structure (DUP-006)
**Severity:** Major
**Occurrences:** 20+ command handler classes
**Locations:** command_handlers.py (11+), superweapon_command_handlers.py
**Problem:** All handlers repeat fleet/planet resolution, existence validation, error returns. Common pre-handler boilerplate: resolve fleet by ID, validate fleet exists, validate fleet belongs to empire, validate fleet has capacity, return ValidationResult on failure.
**Missing Abstraction:** `BaseCommandHandler` with `_resolve_fleet()`, `_resolve_planet()`, `_validate_ownership()` helpers
**Estimated duplicate lines:** 200+

#### Cluster 7: JSON Loader Template (PC-015 + DUP cross-ref)
**Severity:** Major
**Occurrences:** 9 loader/parser classes
**Locations:** strategy/generation/loaders, simulation, UI
**Problem:** No base class. ~100 lines of duplicate open/json.load/error handling/validate/transform code per loader. Pattern: open file → json.load → validate schema → transform → return objects.
**Missing Abstraction:** `BaseJSONLoader` template method class
**Estimated duplicate lines:** 200+

### What Agents Should Investigate Per Cluster

For EACH duplication cluster, agents should determine:

1. **Exact call site census:** List EVERY file and line number where the pattern appears. Not estimates — exact counts.
2. **Variation catalog:** Map the variations. Are all instances identical? What are the differences? Which variations need parameterization?
3. **Proposed API:** Design the concrete abstraction. Include:
   - Class/function name
   - Method signatures with type hints
   - Constructor parameters
   - Example usage showing before/after
4. **Where does it live?** Which module/package should own the abstraction? (game/core/? game/ui/? co-located?)
5. **Migration plan:** Which call sites migrate first? Any that CAN'T migrate? Why?
6. **Test strategy:** What tests exist for the current duplicated code? What new tests are needed for the abstraction?
7. **Estimated reduction:** How many lines saved? (Total current lines → target lines)
8. **Dependency analysis:** Does this abstraction create new imports? Cross-layer coupling? Circular dependency risk?
9. **Risk assessment:** Could this abstraction change behavior? What regressions are possible?
10. **Quick win or project?** Can this be done in a single session (<4 hours) or does it need a phased project?

---

### Special Investigation: Abstraction Design Principles

Beyond individual clusters, agents should recommend:

1. **Naming conventions:** What naming pattern for new abstractions? (Base*, *Mixin, *Utils, *Helper?)
2. **Composition vs inheritance:** When should the abstraction use base class vs mixin vs utility function vs decorator?
3. **Parameterization strategy:** When abstractions need configurability, prefer:
   - Class attributes (e.g., `FONT_SIZE = 14`) for simple config
   - Constructor injection for dependencies
   - Template method for override points
   - Strategy pattern for runtime variation
4. **Gradual migration:** Should old call sites be migrated all-at-once or gradually? What's the policy for mixed old/new patterns during migration?

---

### Special Investigation: Quick Wins vs. Projects

Agents should explicitly categorize each cluster as:

| Category | Criteria | Action |
|----------|----------|--------|
| **Quick Win** | <4 hours, no behavior change, additive only | Do immediately |
| **Small Project** | 1-3 days, touches core code, needs test coverage | Single-phase project |
| **Medium Project** | 1-2 weeks, cross-cutting, phased migration | Multi-phase project |
| **Large Project** | 2+ weeks, architectural change, high risk | Needs separate design review |
