## Instructions

## What we want from you

This is the second-opinion pass before the user starts executing any of the 10 projects. The user's testing philosophy (load-bearing for every project):

- **TDD does NOT apply** — the production code already exists. Use **characterization-style** testing: pin the current observable behavior so tests break if behavior changes.
- **Cover happy path, unhappy path, corner cases** — not every code line, but every meaningful behavioral surface.
- **Do NOT propose production refactors during these projects.** If a plan suggests refactoring code to make it testable, that's a finding (the master plan explicitly forbids it).
- **Apparent buggy behavior should be pinned, not fixed.** Document as observation, file separate ticket. If a plan recommends fixing a bug as part of writing tests, that's also a finding.
- User priority order: **readability > maintainability > functionality > runtime.**

## Specific things to look for

1. **Scope correctness** — are the file lists accurate? Does each project's `manifest.md` match what's actually in the production tree? Do any projects double-count files (i.e. file X listed in two projects' scopes)?

2. **Existing-coverage handling** — multiple plans found that the gap audit's "0 unit tests" claim was wrong (e.g. PROJ-331 found ~159 existing tests, PROJ-336 found ~74 for fleet_navigation_service, PROJ-337 found tests survived PROJ-147 move, PROJ-339 found 3 of 6 panels already have ~17-19 tests each). Verify the projects correctly reframed as gap-fill where applicable. Are any *other* over-claimed gaps still present?

3. **Behavioral coverage adequacy** — do the per-file checklists in each `phase_1_checklist.md` actually cover happy path + unhappy path + corner cases? Or are they predominantly happy-path with no error-handling tests? Pick 2-3 high-risk files (especially `battle_state.py`, `turn_engine.py`, `production_engine.py`, `pathfinding.py`, `system_tree_panel.py`) and check the test plan against the production surface.

4. **Test-name specificity** — checklist test names should describe a single behavior pinned by a single test. Vague names like "test_basic_functionality" are unacceptable; specific names like "test_battle_state_to_dict_roundtrip_preserves_ship_components" are correct.

5. **Mocking / fixture strategy** — does each plan correctly identify where mocks vs real objects vs fixtures should be used? Are there obvious testability blockers the plans missed (e.g. file I/O, global state, threading) and how do they propose handling them? Are any proposed mocks unnecessary (over-mocking)?

6. **Project-boundary file overlap** — the master plan claims zero file overlap between the 10 projects. Verify by cross-referencing each project's manifest. If file X is in two projects, that's a finding.

7. **Sequencing soundness** — master plan says PROJ-331/332/333 are sequential but PROJ-334/335/336 are parallel-safe. Check whether the implied dependencies hold (e.g. does PROJ-332 actually depend on PROJ-331 finishing?).

8. **Effort estimates** — are the session estimates realistic given the test counts and surface complexity? Master plan totals ~20 sessions across 10 projects.

9. **Apparent-bug observations** — several plans record observations of apparent buggy behavior (silent broad-except swallows in turn_engine and battle_state, off-by-one boundaries in services, etc.). Are any of these observations actually correct production behavior misread by the agent? Are any genuine bugs that should be ticketed separately?

10. **Master plan coverage gaps** — does the master coordinating doc miss any high-risk untested files that should be in PROJ-331..340 scope? (Spot-check `game/strategy/` and `game/simulation/` and `game/ui/` for obvious omissions.)
