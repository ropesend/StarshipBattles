## Instructions

Focus areas in priority order:

1. **`_NullBattleResolver` deletion + ValueError-at-dispatch.** The agent removed the null-resolver fallback, changing the failure mode from `logger.warning(...) + RuntimeError on resolve()` to `ValueError at dispatch site` when no `battle_resolver` is wired. Walk every production call site that constructs `TurnEngine` and verify:
   - All sites either pass an explicit `battle_resolver` or the new `TurnEngineConfig.create_default()` populates one.
   - The new `ValueError` message is clear about what's missing.
   - No silent fallback path remains that would swallow the missing resolver.
   - Specifically: `game_session.py`'s constructor + `from_dict` migration looks like the only production consumer; verify that path resolves a real `IBattleResolver`.

2. **`TurnEngineConfig.create_default()` correctness.** The 15 lazy fallback bodies were deleted; their construction logic must now live in `create_default()`. Walk through the classmethod and verify:
   - All 15 (or 18 — the 3 new injectable engines) defaults match the deleted lazy bodies.
   - No engine is constructed with stale or wrong arguments compared to the deleted lazy code.
   - Construction order doesn't expose race conditions (engines that depend on other engines must be constructed in the right order).

3. **Test migration (110 sites, 32 files) soundness.** This is the biggest mechanical migration in the project. Spot-check 5-8 of the migrated tests to confirm:
   - Each test's intent is preserved — the new helper / fixture wires the engines the test was originally configuring.
   - Per-test overrides via `dataclasses.replace(cfg, foo_engine=mock)` produce the same effective state as the old `TurnEngine(foo_engine=mock)` calls.
   - Tests that intentionally omitted `ai_factory` (relying on the deleted `_NullBattleResolver`) were correctly updated.
   - No tests were silently deleted or skipped.

4. **`_run_phases` unification (Phase 4).** The agent collapsed the tick loop and the end-of-turn block into a single shared invocation. Verify:
   - Tick phases and end-of-turn phases really were structurally compatible — no subtle ordering or context-passing difference was papered over.
   - The shared loop's error-handling matches both prior paths (the tick path's exception behavior was different from the end-of-turn path's, historically).
   - `TickContext` is being reused for end-of-turn with `tick=0` sentinel — is this semantically clean, or does it create a confusing dual-meaning context?

5. **AST guards (7 invariants).** Phase 3 added 4 guards; Phase 5 added 3 more. Read each guard in the test files and confirm:
   - Each invariant is meaningful (locks in a real PROJ-369 contract).
   - None are tautological or trivially satisfied.
   - Coverage gaps similar to the PROJ-368 MAJ-002 finding (operator-filter narrowness) — does any guard restrict to specific AST ops in a way that future regressions could slip through?

6. **Sharded suite errors.** The agent reported 3-5 non-deterministic errors in `tests/unit/workshop/` characterized as `pycache/import-mismatch`, unrelated to PROJ-369. Verify with focused test runs whether these errors reproduce; if they do, are they really unrelated or did PROJ-369 disturb something?

7. **`interfaces/engines.py` at 778 LOC.** Plan flagged this. Decisions.md claimed acceptable as interfaces-only. Verify:
   - The file genuinely contains only protocol declarations + dataclasses, not implementation.
   - The architectural justification is real, not an excuse to skip the split.

8. **`turn_engine.py` still 700 LOC.** Over the 500 ceiling. Plan didn't promise sub-500. Is this file structurally splittable, or is it tightly coupled in a way that splitting would create worse abstractions? If splittable, recommend the seam.
