## Instructions

## Instructions

This is a **plan review**, not a code review. The plan proposes migrating the on-disk ticket system at `Tracking/` to GitHub Issues, in parallel with the existing system, while leaving the `Projects/` system entirely on disk.

Review with these questions in mind:

### Soundness of locked design decisions
1. **Status-as-labels (status:* prefix).** The plan models all 9+ existing statuses as labels. Is anything semantically lost? Will agents reliably maintain the 'exactly one status:* at a time' invariant without an enforcement Action? Is there a strictly better design (e.g., GitHub Projects v2 single-select field) that the plan dismissed too quickly?
2. **Close-authority via convention + label gate.** The current system architecturally separates 'agent sets awaiting' from 'user closes'. The plan preserves this via prompt convention plus an optional reopen Action. Is convention sufficient given agent autonomy? What's the failure mode if an agent ignores the rule? Is the optional Action implemented correctly (event filter, sender check, label check)?
3. **Issue body structure.** The plan keeps Description + Acceptance in the body and pushes Work Log / Root Cause / Investigation / Design Review into comments. Does this preserve the rigour of the existing TDD/root-cause workflow encoded in `Tracking/protocols/02_work_ticket.md`, or does scattering work history across comments make the audit trail harder to follow?
4. **Screenshot/log storage as plain repo folders.** No LFS. Public repo. Is `tracking-assets/screenshots/YYYY-MM/issue-NNN-slug.png` the right convention? Image-rendering URL pattern (`?raw=1` query string) — will this work reliably for inline rendering on github.com issues?
5. **Drop BUG-/FEAT- prefixes; use raw issue numbers.** Any cross-reference fragility (existing PROJ-XXX docs, code comments, commit history) that this introduces?

### Correctness of the gh CLI integration
6. **Skill design.** The plan describes 10 new `/claude-gi-*` skills wrapping `gh` commands. Identify any `gh` invocation patterns that won't work as written — e.g., setting multiple labels atomically, label-search filters, attaching comments with multiline bodies via `--body-file`, handling pagination on `gh issue list`.
7. **Authentication/scope.** The plan says auth scopes needed are 'repo, workflow if Actions are added'. Is that correct? Does the optional safety-net workflow actually need `workflow` scope on the user's PAT, or only on the GITHUB_TOKEN it uses?
8. **Issue templates (.github/ISSUE_TEMPLATE/*.yml).** The form-template syntax (issue forms, not legacy markdown templates) is what the plan implies. Confirm the field types described (textarea/dropdown) and the `default labels` mechanism are accurate per current GitHub Issues forms spec.

### Completeness — what's missing
9. **Failure modes** — what happens when `gh` is rate-limited (5000 req/hr authenticated), the network is down, or the user is offline? Should skills fall back to local markdown drafts that sync later?
10. **Migration cutover** — the plan says old system stays running, new system builds in parallel, sunset later. There's no explicit cutover criteria or sunset checklist. Is that a gap?
11. **QA-observer integration** — flagged as out-of-plan follow-up. Is that the right call, or should it be in scope (since it's the primary creator of bug tickets today)?
12. **Authority leak via `gh issue edit --add-label verified`.** The plan's safety net checks for `verified` label at close time, but doesn't restrict who can ADD that label. An agent that adds `verified` then closes would defeat the gate. Is there a tighter design?

### Sanity checks
13. **Projects-out-of-scope decision.** The plan reviewed and rejected migrating the `Projects/` system. Read the 'Projects System — Out of Scope' section. Is the reasoning sound, or have I underweighted any benefit of unification?
14. **'Plain repo folder, no LFS' for screenshots.** With public-repo, every PNG ends up in clone history forever. At what volume does this become painful? Should the plan set a threshold (e.g., 'revisit when tracking-assets/ exceeds 200 MB')?
15. **Dual-tracking risk.** During the parallel period, will agents accidentally double-create tickets in both systems? The plan doesn't describe how `/claude-ticket-*` and `/claude-gi-*` interact when ambiguity arises.

### Bonus
16. Any other concerns — bad assumptions, missing prerequisites, oversights, or 'this looks fine but you'll regret it in 6 months' design smells.

Deliver findings ranked by severity (critical / major / minor / nit) with concrete suggested fixes per finding.

## Context

## Context

User is a solo developer who currently uses a sophisticated markdown-on-disk ticket system at `Tracking/` (165 tickets, 11 protocols, 16 slash commands). They want to start using GitHub Issues so tracking is visible on the project's GitHub page (`github.com/ropesend/StarshipBattles`).

Key constraints from the conversation that shaped the plan:
- **Public repo.** Screenshots/logs committed to repo are world-visible.
- **Agent-first design.** Claude Code agents do most of the ticket work, including image management — drag-and-drop attachment workflows are out.
- **Parallel implementation.** Existing `Tracking/` system stays running as the safety net; new GitHub system builds alongside under a different skill prefix (`/claude-gi-*`). Sunset later, on user's call.
- **New tickets only.** 154 historical archived tickets stay frozen on disk; no bulk import.
- **Authority preservation.** Today, agents architecturally cannot close tickets — only the user can via `/claude-ticket-close`. This must carry forward.
- **Projects system stays local.** Reviewed and excluded — too multi-phase, too tooling-heavy, too internal-facing.

The plan is a `.md` file under `AgentCoordination/opencodereview/plan_under_review/`. It has not been implemented yet. The user wants an independent OpenCode review before approving.
