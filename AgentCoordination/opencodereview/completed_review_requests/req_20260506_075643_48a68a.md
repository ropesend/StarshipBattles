## Instructions

Focus areas in priority order. The decorator-metadata-only contract is the most load-bearing constraint of this project; verify it first.

1. **Decorator-as-metadata-only contract.** This is the load-bearing invariant. The joint Codex+Claude review established: `@command_spec(...)` must attach `handler_cls.__command_spec_kwargs__ = spec_kwargs` and return the class **unchanged** — it must NOT call `command_registry.register(...)` at class-definition time. Verify:
   - Read `game/strategy/engine/commands/registry.py` `@command_spec` implementation. Does it write to the registry at class-def time?
   - Phase 1 added a TDD test pinning this. Find the test (likely `test_import_handler_module_does_not_register` or similar). Read its body and confirm it actually proves the invariant — i.e., it imports a handler module and asserts `command_registry._specs` is unchanged BEFORE `seed_default_commands()` runs.
   - If the decorator did register at import time, what would break? Confirm the test would fail (mentally simulate a regression).

2. **Reset/seed cycle correctness.** `reset_command_registry()` must clear all entries and call `seed_default_commands()` such that the registry returns to default state cleanly. Specifically verify:
   - The reset path doesn't rely on re-importing already-imported modules (cached in `sys.modules` would skip decorators — but decorators are no-op anyway per #1, so this is just a sanity check).
   - `seed_default_commands(registry)` imports modules + calls each module's `register(registry)`.
   - A round-trip `reset → seed` test exists and passes; both default + replacement entries are visible after.
   - Test fixture state isolation: when one test mutates the registry, does the next test see clean state? Look at conftest.py / autouse fixtures.

3. **Facade forwarder collapse — class-level vs `__getattr__` decision.** The agent reported deviating from the design.md plan: instead of using `__getattr__` (which was the design's recommendation), they used a class-level `_install_dispatch_forwarders()` auto-install loop. The reason given: `__getattr__` would have failed `test_strategy_session_facade_public_api` because `hasattr(StrategySessionFacade, name)` and `inspect.getmembers` need class-level visibility. Verify:
   - Read `game/strategy/facade/strategy_session_facade.py` and find the `_install_dispatch_forwarders()` mechanism.
   - Confirm: are all 31 forwarder methods accessible via `getattr(StrategySessionFacade, name)`?
   - Confirm: do they correctly bind `self` so calling `facade.dispatch_X(cmd)` works as before?
   - Confirm: do they preserve return type annotations / docstrings sufficiently for the public-API contract?
   - Was the deviation documented in `decisions.md`?

4. **`COMMAND_SPECS` tuple deletion (`specs.py` deleted).** Verify:
   - The file is genuinely deleted (`ls game/strategy/engine/commands/specs.py` should fail).
   - No remaining import of the tuple anywhere in `game/`, `tests/`, or `docs/`.
   - The AST regression test in Phase 3 (`test_no_specs_tuple_literal.py`) actually catches the regression case (mentally simulate someone re-introducing `COMMAND_SPECS = (...)`).

5. **Consumer migrations.** Walk through the 3 production consumers:
   - `registry_factory.py` — does it iterate the registry instead of the tuple?
   - `action_time_resolver.py` — how does it look up commands by order_type / category? Is the new lookup path semantically equivalent to the deleted tuple path?
   - `command_dispatch_slice.py` — same question.
   - If any consumer relied on a tuple-specific feature (insertion order, slicing, length checks), confirm the registry preserves it or the consumer was updated.

6. **WARP silent-drift cleanup.** The agent discovered a local `MOVEMENT_ORDER_TYPES` frozenset in tests that was missing WARP — fixed during Phase 2. Verify:
   - The canonical frozenset (in `data/order_types.py` or wherever) IS authoritative.
   - The test file change (asserting WARP movement-engine-handled = 0 dispatch hits) is correct, not a relaxed assertion that just makes the test pass.
   - Are there other places in the code that maintained a stale local copy of similar frozensets? Out of scope for fixing here, but worth flagging.

7. **Cross-project handler-file overlap.** PROJ-371 touches files PROJ-370 will also touch: `handlers/base.py`, `handlers/build.py`, `handlers/movement.py`, `handlers/order_queue.py`, `planet_command_handlers.py`. Per the joint review, PROJ-371 ran before PROJ-370 to avoid the overlap window. Verify:
   - PROJ-371's edits to these files don't add new write paths (PROJ-370 will route writes through mutator protocols).
   - The new `register()` functions in these files are pure metadata + dispatch wiring — no business logic added.

8. **Anything else.** Look for: layering violations, broad `except Exception` without rationale comments, missing return-type annotations, files approaching 500 LOC, missing AST guard variants similar to PROJ-368/369 narrowness misses.
