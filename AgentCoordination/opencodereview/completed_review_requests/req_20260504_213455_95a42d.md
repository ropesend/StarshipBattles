## What to look for

All three projects use **characterization-style** testing per user direction. Tests should pin OBSERVED current behavior so they break if production behavior changes. NO TDD. NO production refactors. Apparent bugs documented as observations.

Review these characterization tests against the production code they pin. Look for:

1. **Behavior accuracy** — does the test actually pin what production does? Pick 5-10 tests across the 3 projects, read the production code they reference, and verify the assertion matches actual behavior. A test that passes on accident (e.g., MagicMock returns True for everything) is worse than no test.

2. **Brittleness** — are tests pinning implementation details (private method names, internal data structures) that should be allowed to change? Or are they pinning observable behavior?

3. **Mocking discipline** — over-mocking (e.g., mocking the production class out entirely so the test exercises nothing) vs appropriate-mocking (boundaries only). Pick 3-5 tests with heavy mocking and assess.

4. **Specific test names** — test functions should describe one behavior pinned by one test. Vague names like `test_basic` are bad.

5. **Missed surfaces** — for each project, check the production file's public methods + public state mutations. Are major behaviors uncovered? PROJ-331 + PROJ-334 are gap-fill; PROJ-335 is mostly green-field. Different bars apply.

6. **Apparent bugs documented vs not** — the projects' decisions.md lists OBS-NNN observations. Do the tests actually pin those observations as currently-broken behavior? Are there other apparent bugs the agents missed?

7. **PROJ-331-specific:** verify the `OBSERVATION-A/B/C` from `Projects/active_projects/PROJ-331/decisions.md` are pinned (broad-except in `_collect_team_modifiers`, etc.).
